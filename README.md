# AI 篮球分析软件

> 上传篮球比赛视频 → 自动生成比分 / 命中率 / 球员统计 / 投篮热区 /
> 高光集锦 / 文字战报，并叠加**战术层** —— 控球归属 / 传球网络 /
> 阵型识别 / 空间指标 / **俯视战术图**（可逐帧回放）。
> 面向「算法创新赛道 · AI+软件」方向，基于开源底座二次开发 +
> 自研增量（计分规则引擎、事件融合、热区口径、**战术层算法**）。
>
> 两份实施手册：`docs/实施步骤_比赛分析.md`、
> `docs/实施步骤_战术层.md`。

## 仓库里有什么 / 没有什么（clone 之后先看这段）

**有**：全部源码（`src/` `web/` `scripts/` `tests/`）、实施手册、自检脚本、
前端本地化依赖（`web/vendor/`，约 2.5MB，断网也能演示）。

**没有**（`.gitignore` 主动排除，都是为了控制仓库体积 —— 本机这些加起来 10GB+）：

| 内容 | 本机大小 | 怎么获得 |
|---|---|---|
| 比赛视频 `data/*.mp4` | 单个 34MB ~ 962MB | 自己录 / 自己找；或直接用下面的合成数据 |
| 模型权重 `runs/**/*.pt`、`weights/` | 每个约 5MB | 自己训（`scripts/train_*.py`），或用 YOLO 官方预训练权重 |
| `ffmpeg.exe` / `yt-dlp.exe` | 84MB / 17MB | 见 §3；系统 PATH 里已有 ffmpeg 也行 |
| 分析产物 `out/` | 几百 MB | 跑一次分析就有（随时可重建） |
| 第三方参考代码 `third_party/` | 725MB | 本机参考资料，与运行无关 |
| 任务库 `data/jobs.sqlite`、标定/标注 | 小但与本机绑定 | 运行时自动生成 |

### 只想自动数进球 / 自动算比分（**不读比分牌**）

没有比分牌覆盖层的素材（固定机位拍的比赛、训练、野球场）也能自动计分：

```powershell
# 只要自动计分可以跳过逐帧 YOLO（--fast，CPU 上快十几倍）
python -m aihoop.cli video --video data\nybo_3min.mp4 --cal data\calibration.json `
  --out out\nybo --fast --hoop-weights runs\detect\rim\weights\best.pt
```

判进球靠 `hoopsight.py`：**只看篮筐窗口里「球的尺寸」的运动块有没有
从筐口连续落到网下** —— 不读比分牌，也不要求先追踪到球。跑完会打印：

```
[info] 画面里没有广播比分牌覆盖层 —— 自动计分改走「球 + 篮筐」视觉路径
[ok] 篮下判进球：判出 3 次进球（59.9s、127.7s、173.4s）
       逐帧验证图（可肉眼核对每一次进球）：...\data\hoopsight_verify.png
[warn] 分值只能按经验假设（默认 2 分）：标定把画面里的篮筐投到了 (-5.0, 8.2)……
[ok] 比分 主队 6 : 0 客队 | 出手 3 次
```

每次进球都会在**视频同目录**留下 `hoopsight_verify.png`：把进球前后各若干帧的
篮筐放大图横排，并标出篮圈位置与出筐帧。**自动计数必须能被肉眼复核** ——
这是本工程对「不许编答案」的执行方式。

| 参数 | 作用 |
|---|---|
| `--no-hoop-sight` | 关掉篮下判进球这条路（默认开启） |
| `--hoop-sight-min-drop` | 判进球的总下落下限（× 篮圈半高），默认 1.5；调大更保守 |
| `--visual-shot-value` | 没有可信标定时每球按几分记（默认 2，报告里标注为假设值） |
| `--hoop-weights` | 训练好的篮筐检测权重（强烈建议给：实测帧覆盖率 0.97，启发式只有 1~3%） |
| `--basket-teams "1=home,2=away"` | **人工指定第 N 个进球是哪一队**（自动判不出时用，见下） |
| `--basket-lookback` | 「向前找」多少秒（默认 1.5）—— 这个数字是在有真值的素材上标定出来的，见 §验证 |

#### 实测验证：「进球检测」和「分队」各有多少准头

**① 进球检测（`data/nybo_3min.mp4`，3 分钟）**——用一套**独立**参考答案交叉验证：
只按「篮筐正下方一小块的运动能量」找峰值（不看球的形状、不看下落轨迹），
全片得到 4 个峰值簇：59.85~59.93、126.58~128.50、172.30~173.46、174.80~174.97。
`hoopsight` 判出的 3 次进球（59.94 / 127.67 / 173.42）**逐个对上**前 3 簇；
第 4 簇（174.8~175.0）我逐帧看过，是前一次进球后**网还在晃**，不是新进球。
→ **漏判 0、多判 0**。

**② 分队（`data/basketball_match.mp4`，3 分钟转播，有比分牌）**——这一段能算准确率：

| 比分牌真值 | 数值 |
|---|---|
| 得分事件 | 8 次（2 分×4、3 分×2、罚球×2；主队 7 次、客队 1 次） |
| 逐次比分 | 与最终读数 15:6 对得上（带入分 0:5 单独记账） |
| 读帧命中 | 1697 / 1802 帧 |

把「比分牌说谁得分」当真值，衡量几种归因规则的准确率：

| 归因规则 | 判对 | 判错 | 未定 | 有效准确率（判对/(判对+判错)） |
|---|---|---|---|---|
| 进球**瞬间**离被进攻篮筐最近的球员属哪队 | 4/8 | 4 | 0 | 50% |
| 进球前 0.5s | 5/8 | 3 | 0 | 62% |
| **进球前 1.5s**（「向前找」） | 6/8 | 2 | 0 | 75% |
| 进球前 3.0s | 5/8 | 3 | 0 | 62% |
| 进球前 1.5s **+ 距离门槛 1.5m**（当前默认） | 4/8 | **0** | 4 | **100%** |

**为什么"瞬间"反而最差**：进球那一下，站在篮筐下面的大多是**防守人 / 抢篮板的人**，
投进的人已经落地或转身了；往前看 1.5 秒，球还在进攻方手里 —— 这就是
「向前找最后持球的人」比「看谁在筐下」准的原因。该结论已落进代码：
`baskets.DEFAULT_LOOKBACK_S = 1.5`，`--basket-lookback` 可调。

**距离门槛为什么取 1.5m**：两个判错的样本，最近的球员都在 1.9m / 0.9m 外
而且都是**防守方** —— 这种球"最近的人"本来就不是答案。加上门槛后
**凡是我们敢判的，全对**（4 对 0 错），代价是另外 4 次标成未定。
这符合本工程的取向：宁可说"这球判不出，请人工定"，也不给一个错的队别。
（门槛表格：`out/tmp/threshold_effect.py`。）

**参数网格**（向前的秒数 × 看最近几人 × 投票/最近者优先/距离加权，共 75 组）
最佳也只有 6/8 —— 说明瓶颈不在参数，而在"最近的人"这个特征本身；
它在这一段素材上已到顶。

**③ 队别标签不需要"锚定"；真正拖后腿的是标定与球的可测性**：
一开始我怀疑 8 次事件里有整体判反（那就要去比对球队名文字），做了两件独立的核对：
1. **混淆矩阵**：1.5s 前瞻是 6 对 / 1 个 home→away / 1 个 away→home —— 不是整体翻转；
2. **颜色锚**：这段村BA 的比分牌把**队名框刷成了本队球衣色**（左「中华橘源队」青绿、
   右「超级草根队」橙色），拿它给每个球员的球衣主色重新判队，得到的映射是
   **恒等映射**（home→home 85 票、away→away 103 票），加锚后 6/8 **没有变化**。
   → 两条都否掉了"标签反了"这个假说，**不用去做 OCR 锚定**。

但核对过程中挖出一个**真问题**：`basketball_match` 那份标定是**坏的** ——
把它反算 (0,±1.575) 得到像素 (639,672)/(641,760)，而那段素材的篮筐在画面
另一端 (≈900,160)，反算位置落在比分牌覆盖层上（见 `out/rim_moments_match.png`）。
用这种标定算出来的球员坐标是垃圾（"离篮筐最近的球员"其实离筐 20m 外）。
`nybo` 那份标定**同样坏**：反算篮筐到 (836,446)，实际在 (72,58)，相差上千像素。
（`reproj_error_m = 0.0` 只说明手输的 4 个角点自洽，**不代表它们是球场角点**。）

教训已落进代码与流程：
* `baskets.calibration_sane_for_scoring()` 拿**画面里检测到的篮筐**校验标定，
  投不到真篮筐附近（>3m）就判为不可用于判分值/判队；
* 判队改用**像素空间**（`attribute_by_pixel_lookback`）：球员脚底点是直接观测值，
  **标定坏了也不受影响**；球场坐标版只在标定通过校验时才启用；
* `out/tmp/check_calibrations.py` 一条命令复现三份标定的体检结果。

**④ 「追球 → 最后持球人」在这批素材上做不到（已量化，不是没试）**：

| 测法 | 结果 |
|---|---|
| 专用球检测器 | 整段 2.5s 窗口内离筐 <260px 的候选 **0 个** |
| 橙色掩码（球衣/地板同色） | 每帧 26 个候选，面积中位 236px —— 框到的是红球衣和地板 |
| 亮度+运动小亮点 | 每帧约 **1000** 个（观众脸、反光） |
| 进球时刻逐帧看筐口 | 720p 里球只有约 6~10px，且被遮挡 |

结论：「向前找最后持球的人」需要球可见，而这段素材（720p 广播 + 密集人群）
提供不了。要真做，得先针对广播机位**补标注训练球检测器**（`scripts/label_rim.py`
那套流程可复用），并接受它只在球未被遮挡的少数帧有效。

#### 「这一球是哪一队进的」怎么定、什么时候定不了

判据按可靠度分四档，代码只用**确实成立**的那一档：

| 档 | 判据 | 说明 |
|---|---|---|
| A | YOLO 球员框里**筐下**最近的人（像素坐标） | 上篮/补篮的人就在筐下，最硬 |
| B | **篮筐窗口里的「人形运动块」** + 球衣色对表 | A 不成立时用；块的上半部主色 vs 两队球衣色 |
| C | 整段「近筐球员采样」的球衣颜色投票 | 很粗，只当参考 |
| D | 都不成立 → **留空（未定）** | 只报证据，不猜 |

为此专门保留了两样东西：球员在**画面像素坐标**下的观测（`raw_track.json`
的 `player_obs`），以及每帧在篮筐附近找到的**人形运动块**（`hoopsight.people`）。
用像素而不是球场坐标，是因为判进球发生在篮筐那一小块区域，像素距离是直接
测量值；用投到地面的坐标会被坏标定带偏（实测一份错标定把画面里的篮筐投到了
离真篮筐 8.3m 处，离筐 1m 的人会被算到 8m 外，进球直接记到别队头上）。

**B 档的「人」判据靠形状、尺寸、填充率，不是面积。** 实测三个坑：
* 「球穿过网」那一瞬间球和网会连成一个 1200~1700px 的方块（长宽比≈1），
  面积跟远处一个人差不多 —— 只看面积一定把球+网当成人；
* 快速运动的**拖影**（实测 42x71）长宽比像人但是糊的；
* 更坑的是：给视频烧进去的**文字/字幕**在后续帧里会被背景差分当成前景，
  长宽比、面积都像人 —— 结果「筐下检出人」检到的是我自己画上去的字。

所以现在要求：高/宽 ∈ [1.4, 4.5]、高 ≥ 110px、面积 ≥ 2200px、**填充率 ≥ 0.45**。
`tests/test_hoopsight.py` 里有合成画面的 4 个正/反用例（筐下真站一个人 →
检出并读到黄色；球+网方块 → 不报；远处的人 → 不报；文字笔画 → 不报），
所以「0 个」这个结论有说服力：**是素材里没人，不是检测器不会检**。

**实测 `data/nybo_3min.mp4` 的结果是 D 档**：
* YOLO 全场**没有一帧**在篮筐附近检出过人（最近的一次 359px ≈ 4 m）；
* 只有篮筐窗口的「人形运动块」检过：**0 个**（三次进球前 2.5 秒窗口内都没有）；
* 于是三次进球都标 `未定（unknown）`，`value_source="team_unknown"`，
  并把证据打出来：「t=59.94s 时场上最近的是 T1518（home，532px ≈ 5.9m）」。

分队本身也带可靠度：球衣颜色对照表用**全队所有采样**的众数，并给出
`legend_confidence`。实测主队=黄（可信，53/77 采样是黄）；另一队标 `灰色` 且
`uncertain` —— 浅色球衣在阴影里同时读成灰 63 / 白 12 / 蓝 59，与其嘴硬给一个
颜色，不如标不确定。

三张可复核的图（都在视频同目录）：

| 文件 | 看什么 |
|---|---|
| `hoopsight_verify.png` | 每次进球前后各若干帧的篮筐放大图 —— 球确实进网下落 |
| `hoopsight_people.png` | 每次进球前后**筐下检出的人形块**（框+球衣色块+离筐距离）；没有就明写「筐下确实没检出人」 |

### 进球判定：从"手调阈值"升级为"学出来的模型"

手写判据在 `nybo_3min` 上 precision = 0%（3 个判定全错），而且**调阈值救不了**
（误报的置信度高达 0.97）。所以补了一条**训练链路**：

```powershell
# 1) 导出训练数据：正样本来自有比分牌真值的转播片段，负样本是其他时刻
#    （篮筐位置由球场标定反算，不需要篮筐检测器）
python scripts\export_basket_patches.py            # → out/basket_ds

# 2) 训练：小 CNN（两张相隔 0.12s 的 96×96 篮筐切片）+ 逻辑回归对照
python scripts\train_basket_model.py --ds out\basket_ds --out out\basket_model

# 3) 分析时带上模型：用模型分数替代手写阈值
python -m aihoop.cli video --video data\nybo_3min.mp4 --cal data\calibration.json `
  --out out\nybo_model --device 0 --fast --basket-model out\basket_model
```

**实测（数据规模很小，如实标注）**：

| 模型 | 输入 | 留一法 AUC | nybo（人工真值：0 进球）误报 |
|---|---|---|---|
| 逻辑回归 | 7 个数值特征（网动/环带能量比、球块位置…） | **0.39**（比随机还差） | 2 个 |
| **小 CNN** | 两张 96×96 篮筐切片 | **0.89** | **0 个** |

- 训练集：`basketball_match.mp4` + 比分牌真值 → **8 正 / 126 负**；
  测试集：nybo 的 7 个候选（用户标注全为"没进"）。
- **正样本只有 8 个**，AUC 是留一法估计，只说明"链路能学、方向对"，
  **不能当生产级指标**。样本越多越准，而样本来源已经打通：

**界面上每确认一球，样本就多一个**（高光页 → 「进球确认」→ 选"进了/没进" → 提交）。
这些判断会：

1. 写进 `data/basket_feedback.jsonl`，**同一段视频重跑分析时自动用于过滤误报**
   （不用再填任何路径）；
2. 同时是带人工标签的训练样本 —— 随时可以重跑上面第 1、2 步把模型重训一遍。

### ⚠️ 失败案例：球追不到时改看"球员动作"——单素材看着好，**跨素材不成立**

`data/bili_nybo.mp4` 是"球只有 5~15px、追球类方法全部失败"的素材。
一个自然的想法是**不看球、只看人**（YOLO 姿态 → 起跳 / 筐下聚集 / 骨架摆动）。
在用户标注的 32 个候选（14 进球 / 18 没进）上做留一法，结果**看起来非常好**：

| 检验 | 结果 |
|---|---|
| bili 内部留一法 | AUC **0.898**、F1 0.82（精确率 71%、召回 95%） |
| **跨素材：bili 训练 → `sample_dairy.mov` 测试** | AUC **0.462**（比随机还差） |

跨素材检验里，`sample_dairy` 那 **2 个逐帧确认过的真进球**在 15 个窗口里只排到
第 6、第 11 名（分数 0.070 / 0.118，而负窗口中位是 0.092）。

**结论：那个 0.898 是过拟合** —— 模型学到的是"这段场馆/机位的统计特征"，
不是"进球"这个事件本身。**所以"看球员动作"目前不能作为判据。**

复现：`python scripts\pose_crossval.py`（明细见 `out/pose_crossval.json`）

**教训**：任何只在单段素材上做留一法的指标都不足为据 ——
必须像上面这样**留出另一段素材**做交叉检验，否则会得出"看着 0.9、实际 0.46"的错误结论。
本项目所有指标都应附上"是单素材还是跨素材"的标注。

### ⚠️ 失败案例：自动球场标定（关键点模型）在换机位后不成立

思路：用公开数据集训一个球场关键点模型（YOLO-pose），自动识别场地关键点 →
解单应矩阵 → 自动标定，替代"人工点 5 个点"。

实测链路与结果：

| 环节 | 结果 |
|---|---|
| 数据集 | Roboflow "Basketball Court Detection" v9，203 张，CC BY 4.0，平均可见 12.2/14 个点 |
| 训练 | pose mAP50 **0.83**（验证集） |
| 关键点→球场坐标映射 | **实证推导成功**（134 张图，以四角为锚，各点离散度大多 <1m）|
| 在用户视频上 | 认出 14/14 个点，重投影误差 1.6~2.4 m（**内部自洽**）|
| **独立校验（人工标定的真篮筐）** | **偏 23.45 m；加入 3 帧人工标注微调后仍偏 17.07 m → 不可用** |

**这条最值得记住**：只拟合误差（1.6 m）会得出"标定可用"的错误结论；
**必须用画面里一个与关键点模型无关的真值点（这里是人工标的篮筐）做独立校验**，
才能发现它偏了二十多米。这与"成功案例 1"里的做法是同一条原则。

**结论**：手动标定（界面上点 5 个场地特征点）虽然费 30 秒，但**结果是可靠的**，
仍是当前唯一可用的标定方式。自动标定要成立，需要**大量**该机位的标注（3 帧不够）。

相关脚本：`scripts/train_court_keypoints.py`、`scripts/derive_court_kp_map.py`、
`scripts/verify_court_kp_map.py`、`scripts/auto_calibrate.py`、`scripts/mark_court_kp.py`
（映射文件 `data/court_kp_map.json`）

### ⚠️ 失败案例 13：合成小球检测器（领域随机化）也不行

思路：既然"人眼标不准 5~15px 的球"是训练数据的瓶颈，就**不标真球** ——
用程序合成橙色小球（含按真实速度的运动模糊）贴到**你视频的真实背景帧**上，

### 自动计分是怎么做的（这条链路的重点）

COCO 预训练的 YOLOv8 里**没有「篮球」这个类**（只有 sports ball，远景 720p 画面
几乎不触发 —— 实测一段 3 分钟的真实比赛只命中 2 个点）。所以「靠检测球来数比分」
这条路走不通，硬做只会得到 0:0。

系统里有**两套互相兜底的自动计分路径**，按素材有没有比分牌覆盖层自动选：

#### 路径 A：广播比分牌（比赛转播、有台标覆盖层）

| 证据 | 模块 | 负责什么 | 可靠性 |
|---|---|---|---|
| 广播比分牌 | `scoreboard.py` | 谁、什么时刻、得了 1/2/3 分 | 高（导播系统直接渲染，零噪声） |
| 球轨迹 | `ball.py` | 出手位置、打铁候选 | 中（单目估计，标 `location_estimated`） |

比分牌只告诉你「谁得了多少分」、不给位置；球轨迹给位置、但经常追不到。
所以让比分牌管**计分与命中判定**，球管**位置与出手归因**，两者互补。
球员身份用球衣颜色聚类分成主/客两队。

比分牌识别**不需要 OCR 库、不需要训练**：多帧颜色投票定位台标 → 白色文字行投影
切出比分行 → 按**词结构**定出「主队得分 / 节次 / 客队得分」三个字段中心 →
把**整个字段窗口当图案聚类匹配**（而不是逐字识别数字）→ 比分只增不减的时序去抖。

> 为什么不逐字识别：两位数（"10"/"13"）在 JPEG 下粘成一个连通域，而缩放归一化
> 又会抹掉宽度信息（这个台标字体里「1」9px 宽、「7」16px 宽，拉完几乎一样）。
> 窗口图案法把分割、归一化、字体三个坑一次绕开，代价是每个频道人工标注一次图案。

#### 路径 B：球 + 篮筐（手机拍的野球场、训练视频 —— **没有比分牌**）

| 步骤 | 做法 |
|---|---|
| 认篮筐 | 逐帧找「橙色 + 又宽又扁」的色块（篮圈）和「高亮低饱和矩形」（篮板），**按时间存成轨迹**；有训练权重时用 YOLO 篮筐检测器（实测帧覆盖率 97%） |
| 认球 | 橙色色块 + 运动显著性多线索，再用速度外推连成轨迹（`ball.py`） |
| **篮下判进球** | **`hoopsight.py`：只在篮筐窗口里看「球的尺寸的运动块」有没有从筐口连续落到网下** —— 不依赖球检测器，也不需要全场追球 |
| 判进球（细粒度） | 球**从篮筐平面上方落到下方**，且穿越点落在篮圈内（相邻两帧线性插值） |
| 归属 | 先按「穿筐时刻离筐最近的球员」定队，再退回近筐球员的球衣颜色投票 |

关键点：**判进球全程在图像空间里做，不需要知道球离地多高** ——
所以它绕开了「单目没法测球高度」这个老问题。
另外，手持/摇摄画面里篮筐会移动（实测一段 27 秒视频里漂了 45×64 像素），
所以用的是**每一帧各自的篮筐位置**，不是一个全局中位数。

> **为什么还要 `hoopsight.py` 这一层：** `ball.py` 那条路要求先把球追成一条完整弧线，
> 而球检测器在固定机位远景素材上经常整段失效 —— 实测一段室内青少年比赛里，
> 检测器认的是**黄色球衣**（每帧 1~5 个框全在球员胸口），真正的蓝黄拼色篮球
> 几乎没被框到，于是 186 条候选轨迹里没有一条能形成投篮弧线，输出 0 次出手。
> 但**进球这件事本身在画面上是直接可测的**：篮筐静止、位置已知，
> 球进筐时篮圈窗口里必然出现一个「球的尺寸」的运动块（球 + 被带动的网），
> 并在几百毫秒内从筐口连续下落到网下。
>
> 实测 `data/nybo_3min.mp4`（3 分钟，固定机位，画面里**没有比分牌**）：
> 自动判出 **3 次进球**（t≈59.9s / 127.7s / 173.4s），每次都有逐帧验证图
> （`out/hoopsight_verify.png`），肉眼可核对球确实是穿筐落网的。
> 分值：没有可信出手坐标时按 2 分计并标注「分值来自估计」。

这条路径**不需要球场标定**，但也就**分不出 2 分和 3 分**（单目图像距离无法可靠
换算成米 —— 投篮的人离相机比篮筐近得多，透视尺度差好几倍）。这时按默认分值计，
并在战报里明确标注「分值是按经验假设的」。

> **视频从半场中间开始录怎么办？** 路径 A 里首帧读到的比分就是「开局带入分」，
> 会计入总分（报告里明确标注），但**不会伪造出手事件**去凑分。

## 5. 坐标系契约（改代码前必读）

**全场只有一套坐标，不要颠倒：**

| 轴 | 含义 | 范围 | 说明 |
|---|---|---|---|
| x | **横向**（球场宽度方向） | −7.5 ~ +7.5 | x=0 是球场中轴，\|x\| 越大越贴边线 |
| y | **纵向**：符号表示在哪半场，\|y\| 是**离本方底线的距离** | −14 ~ +14 | \|y\|=0 是底线、\|y\|=14 是中圈；\|y\| 越大越靠近**中场** |

* 篮筐在 **(0, ±1.575)**：`HOOP_LEFT = (0, −1.575)`、`HOOP_RIGHT = (0, +1.575)`
  （1.575m = 篮筐圆心距底线；只有把 \|y\| 当「离底线的距离」才对得上）
* ⚠️ 这是**折半坐标**：两个半场叠在一起，两条底线都是 \|y\|=0。
  好处是热区图 / 分区统计 / **俯视战术图**都只需要画一套半场，左右天然对齐。
* 攻哪一侧由 **y 的符号**决定：y<0 攻左篮筐，y>0 攻右篮筐
* 三分线：弧半径 6.75m（圆心=篮筐）；底角直线距边线 0.90m，判据是 **|x| ≥ 6.60（横向！）**
* 前端 `web/court.js` 的 `mapXY` 把数据坐标映射到画布：半场视图 u=\|x\|、v=\|y\|，
  画布 v=0 是底线、v=14 是中场线，所以篮筐**画在 (7.5, 1.575)**

> ⚠️ **这里踩过一个真实的坑，已修并加了回归测试。**
> 早期版本 `rules.py` 把 x 当纵向（距篮距离）、y 当横向，而 `shot_chart` 的网格、
> `court.HALF_COURT_CORNERS`、前端 `court.js` 都把 x 当横向、y 当纵向。
> 后果：① 底角三分被 clamp 到网格最后一行，热区图整体压扁；
> ② 用标定角点算出的坐标喂给计分引擎时轴被交换，篮下上篮会被判成三分。
> 现在 `tests/test_plan_a.py::test_axis_frame_consistency` 会守住这个契约，
> 另有 `web/_validate.js` 用 0.25m 网格扫描交叉校验前端 JS 与后端 Python 的分区口径。

## 6. 自研增量在哪（答辩重点）

| 模块 | 位置 | 为什么算增量 |
|---|---|---|
| 计分规则引擎 | `rules.is_three_pointer` / `shot_value` | 按 FIBA 几何（弧 6.75m + 底角直线 0.90m）判 1/2/3 分，只对被进攻篮筐计算，踩线算 2 分 |
| **广播比分牌识别** | `scoreboard.py` | 免 OCR 库、免训练：定位台标 → 词结构定字段 → 字段窗口图案匹配 → 比分只增不减的时序去抖。**这是「3 分钟视频跑出 0:0」的修复**，也是自动计分的主证据 |
| **多线索球追踪** | `ball.py` | YOLO + 橙色色块 + 运动显著性三路候选，再用「速度外推 + 门限」连成轨迹；单帧候选都不可信，可信的是连成轨迹的那条 |
| **篮下判进球（不靠比分牌、不靠球检测器）** | `hoopsight.py` + `baskets.py` | 把问题缩小到「篮筐周围一小块窗口里的运动块时序」：球的尺寸 → 入筐 → 连续下落到网下 → 穿筐点落在篮圈内。**摆脱了「必须先追到球」这个前提**，实测在一段球检测器完全失效（把黄球衣当球）的素材上判出 3 次进球，逐球附逐帧验证图 |
| **篮筐自动识别 + 免标定进球判定** | `hoop.py` | 逐帧找「橙色且又宽又扁」的篮圈，按时间存成轨迹（手持画面里篮筐会漂移几十像素）；进球判定 = 球在图像里从篮筐平面上方落到下方且穿越点在篮圈内 —— **不需要知道球离地多高**，绕开单目测高难题 |
| **证据分工** | `sources.VideoSource` | 有比分牌就用以计分、球轨迹管位置；没有比分牌就自动切到「球 + 篮筐」路径；标定文件分辨率对不上时拒绝复用，绝不硬套 |
| 命中事件融合 | `rules.fuse_outcome` | 球穿筐 + 记分牌跳变 + 网动三路证据加权投票，输出置信度 |
| 免训练进球判定 | `rules.detect_rim_events` | 用球轨迹几何（进筐圆柱 + 高度下穿）判进球，不依赖训练 |
| 低置信度复核 | `api.correct_shot` | 人工一键改判，全量统计/热区/战报立即重算，口径始终一致 |
| 热区口径 | `rules.zone_of` / `shot_chart` | 以「被进攻篮筐」为基准的分区 + 网格热力，左右半场自动镜像 |
| 合成数据源 | `sources.synthetic_game` | 零依赖生成「像真的」一场比赛（约 40% 禁区、30%+ 三分），用于开发、CI 与答辩兜底 |
| **战术层（B 的核心）** | `tactics.py` | 控球归属 → 传球事件 → 有向传球网络；进攻落位（五外/四外一内/三外两内/双塔/转换）与防守阵型（人盯人 / 2-3 / 3-2 / 1-3-1 / 前场施压）识别；空间指标（凸包面积/平均间距/宽度/纵深/重心到篮筐）。全部是**可解释几何规则**，判据随结论一起输出，纯 Python 零依赖 |
| 俯视战术图 | `tactics.build_tactics_frames` + `web/court.js` | 把球员逐帧球场坐标输出成 JSONL，前端用两层同 viewBox 的 SVG 叠出「球场 + 球员 + 球 + 轨迹」，可播放/拖动/倍速 |
| 标定坐标系修复 | `court.HALF_COURT_CORNERS` / `fold_to_analysis` | 老版本半场标定把底线放在 \|y\|=14，与计分/热区/前端全部相反：篮下上篮被判成三分、战术图整体偏 14m 且不报错。已修 + 回归测试 |

## 7. 已知限制（写清楚比藏着好）

1. **比分牌图案需要一次性人工标注**：`scoreboard.py` 不做逐字 OCR（原因见 §3），
   而是把「字段窗口图案」聚类后人工给数值。每个频道/每台机位标注一次（几十秒），
   同一频道的后续视频用 `--reference` 直接继承。
   **视频里没有比分牌覆盖层时会自动切到「球 + 篮筐」路径**（见下一条）。

   > **比分牌几何是按视频缓存的（`data/scoreboard_bugs/<指纹>.json`），复用时先验证。**
   > 老版本把它存在一个全局 `data/scoreboard_bug.json` 里无条件复用，踩过一个很隐蔽的坑：
   > 某段视频自动定位到的「比分牌」其实是**木地板色块** (406,634,398,75)，
   > 换视频后继续用这个框 → 整片 1440 帧一帧都读不到 → CLI 只打印
   > 「比分牌：读到 0/1440 帧」，看起来像「这段视频没有比分牌」。
   > 现在 `bug_looks_valid()` 会抽帧检查「框里真有白字吗」，判不过就当它失效、
   > 重新定位；定位不出就明确报「画面里没有广播比分牌覆盖层」。
   > 旧版全局文件不再读取。

2. **没有比分数字的记分牌读不出来**：只有比赛计时/24 秒的 LED 板
   （例如固定机位拍的青少年比赛，`data/nybo_3min.mp4` 就是这种）**不含比分**，
   台标路径和 OCR 都拿不到分。这时只能靠「球 + 篮筐」路径，
   而它依赖球检测器在这批素材上的召回 —— 球检测器对不上的素材会**如实返回 0 次出手**
   （宁可空着也不编一个比分出来），请用 `--attempts` 人工标注出手时刻兜底。

3. **没有球场标定时分不出 2 分和 3 分**：路径 B 的进球判定与坐标无关，
   所以比分和命中数是准的；但「这一球是 2 分还是 3 分」需要球场几何才能判断。
   没有这个机位的标定时按默认分值计，并在战报里标明。要精确，
   先 `python -m aihoop.cli calibrate` 标一次机位。
4. **路径 B 的出手归属依赖球员检测**：用「出手时刻离球最近的球员轨迹」，
   球员检测可以抽帧（`--player-stride`），但**球追踪必须逐帧**
   （球在空中只有 1 秒左右，抽帧会整条弧线连不起来 —— 实测 stride=2 时
   6 次出手只检出 5 次）。认不出球员时按出手点左右粗分，并在战报里说明。
5. **出手位置是估计值，不是测量值**：单目相机 + 单应只能把地面点映射到球场坐标，
   球在空中时投到地面会有系统偏差。球轨迹给出的位置一律标
   `location_source="ball_track"` + `location_estimated=True`；
   追不到球时退到「被进攻篮筐」的占位坐标并标 `rim_placeholder`，
   这时**不输出热区**（与其画一张全是「禁区」的假热区，不如空着）。
6. **真实视频的球高度仍是硬编码 `z=1.2`**：`rules.detect_rim_events` 要求 z 穿越 3.05m，
   所以那一路在真实视频上不触发。但路径 B 的进球判定走的是
   `hoop.detect_shots`（图像空间），**不受这个限制**。
7. **单目测距有误差**：摄像机俯角小时纵向误差会放大，建议机位高度 3~5m、俯角 15~30°，
   并用重投影误差 <0.5m 作为标定合格线。
8. **球员身份识别**：目前按球衣颜色聚类分主/客两队；颜色分不开时（例如两队都穿深色）
   退回「出手最多的球员 = 主队」，球员个体用跟踪 ID 占位；球衣号 OCR 还没做。
9. **实测结果**：
   - `data/basketball_match.mp4`（3 分钟转播，有比分牌）→ **15 : 6**，
     逐次得分事件与画面对得上，比分牌读取帧命中率 94%。
   - 一段 27 秒手机拍的室外 1v1（**没有比分牌**）→ 识别出 **6 次出手、命中 5 次**，
     出手时刻与画面里「球在空中」的时刻一一对应；因为该片段里只有一个人在投，
     所以比分是 10 : 0。逐帧验证图确认命中的球确实在网里、未中的确实三不沾。
   - `data/nybo_3min.mp4`（3 分钟、固定机位、**画面里没有比分牌**，
     只有比赛计时 LED）→ 自动判出 **3 次进球**（t≈59.9s / 127.7s / 173.4s），
     按默认 2 分计为 **6 : 0**；`hoopsight_verify.png` 里每一次进球都能看到球进网下落。
     这条链路上**球检测器是失效的**（它认的是黄色球衣：每帧 1~5 个框全在球员胸口，
     真正的蓝黄拼色篮球几乎没被框到），所以「先追球再判进球」的老路给出 0 次出手 ——
     换成篮下判进球后才拿到结果。这说明：**进球判定不必依赖球追踪**。
     分队在这段素材上**判不出**：YOLO 全场没在篮筐附近检出过人
     （离筐最近一次 359px ≈ 4 m），代码如实标 `未定` 并给出证据，
     不拿「场上最近的人」凑答案；`hoopsight_team.png` 是人工定队用的核对图
     （球员框 + 队别/采样球衣色 + 色块 + 图例）。球衣颜色对照：
     主队=黄（可信），另一队=灰/白（`uncertain` —— 浅色球衣在阴影里
     同时读成灰 63 / 白 12 / 蓝 59，不嘴硬给一个颜色）。
     分值只能按经验 2 分：该机位的标定把篮筐投到了离真篮筐 8.3m 的位置，
     已被自动判定为不可用于判 2/3 分。
10. **前端未在真实浏览器验证过**：开发环境无法访问 CDN，只做了 Node 等价自检。
   请在联网环境打开一次 `web/index.html` 确认 Vue/Element Plus/ECharts 正常加载。
11. **战术层的实测**：合成数据（seed=7 / 1800s）跑出 **157 回合 / 215 次传球 /
    24 次球权转换**，两队各识别出 5 名球员的传球网络（20 / 18 条连线），
    阵型在「双塔 / 三外两内 / 四外一内 / 五外」与「人盯人 / 2-3 / 3-2 / 1-3-1」
    之间切换并与生成的防守站位一致；俯视战术图 2647 帧。
    前端 `web/_test.js` 第 [5] 组覆盖战术图层渲染与坐标系对齐。

12. **战术层的球场坐标有两条来源，第二条会显式标注「未校验」**：
    - **① 静态标定（已校验）**：用户标过球场、且通过了自动校验
      （分辨率/机位匹配 + 球场线吻合度 + 画面里的真篮筐能对上），
      `tactics.json` 里 `position_source="static_calibration"`。
    - **② 自动逐帧标定（兜底）**：静态标定不可用时，
      `sources.VideoSource` 会**自动逐帧拟合球场线**解出每帧的单应矩阵
      （`calibcheck.sliding_calibration`），球员坐标就是这条路出来的。
      它要过**两道**关才允许出战术图：
      a. 质量读数「锚点 ≥2、达标率 ≥0.5、中位 ratio ≥1.25」；
      b. **独立校验**：拿人工标的篮筐（同一时刻）经这份标定投回地面，
         必须落在真篮筐 `(0, ±1.575)` 的 3m 内（`validate_sliding_with_hoop`）。
      过关后 `tactics.json` / `game.json` 仍带 `position_unverified=true`
      与 `position_note`（战报第七章 ⚠ 免责段 + 战术页黄色警示条）。
      **b 这道关是必须的**：实测这段素材的逐帧标定把手标篮筐投到 **9.2m** 外，
      而它自己的质量分 ratio 高达 **7.17**（比"看着还行"的锚点 1.4~2.9 还高）——
      线拟合分根本不能证明坐标对，只有与拟合无关的真值点才能发现它。
    - 两条都不满足时**不出**战术图，并说清"离出图还差什么"
      （`game["tactics"]["reason"]` 会直接写"自动逐帧标定没通过独立校验：
      人工标的篮筐经这份逐帧标定投到 (0.0, 11.2)，离真篮筐 9.20 m"）。
    - **为什么要这条兜底**：真视频里静态标定经常通不过校验（镜头在动、
      或用户那份标定点位本身就错），而球员坐标其实是有的 —— 老版本只看静态
      标定的结论就整层跳过，用户看到的是"球员明明检测到了、战术页却一直空着"，
      完全不知道原因（实测踩到）。

13. **标定页现在会自动做两道客观体检**（保存前就拦，给人话原因）：
    - **点位退化**：点几乎在**同一条线**上 / 有重合点。这时单应矩阵在点位上是
      **精确解**，**重投影误差必然是 0.00m 左右** ——"误差很小"完全不能证明
      标定可用（实测一份 4 点标定误差 1.45m、界面显示"可用"，而画面里的篮筐
      被投到 `(-31.0, -14.0)`、离真篮筐 **33.4m**，热区与俯视战术图整片错位
      且不报任何错）。判据是点集的**二维展开度**（最大三角形面积占画面 <0.8%、
      占球场 <0.25%、最近两点 <2px/0.25m），见 `court.calibration_degeneracy`。
    - **独立校验**：这份标定解释得了**画面里那个真篮筐**吗？用户标过篮筐时，
      这是与特征点无关的真值；偏超过 3m 就一票否决
      （见 `baskets.calibration_sane_for_scoring`）。这道校验以前只在
      「篮下判进球」那条路径里跑，**有比分牌的转播会整条绕过它** ——
      实测 `basketball_match` 那份标定把篮筐投到了 **87.3m** 外却照样出图，
      现在提前到 `VideoSource` 里对所有路径生效。
    - 不合格时**不写盘**并返回人话原因（`/api/calibrate`、
      `/api/calibrate_multi` 的 `note` + `degeneracy` + `hoop_check`），
      标定弹窗直接显示；热区/战术图也不会基于这种标定生成。

14. **比分牌：自动定位改成「找全片唯一不动的区域」，OCR 只认那一块**（真视频实测）：
    - 老做法按「饱和色横条 + 长宽比 3.2~11 + 高度 ≥28px + **只在画面下三分之一找**」
      定位。这段 960×544 校园转播的台标是**深蓝长条**（570×24，长宽比 23.8）、
      在**画面顶部**、而且底色与背后的蓝墙同色 —— 四个条件全不满足，
      于是报「画面里没有广播比分牌」，而画面里明明写着 `KPHS 27 : AHS 35`。
    - 新做法 `locate_score_bug_static()`：比分牌是**导播叠加的图形**，
      全片**逐像素几乎不变**（只有数字会跳），而球员/看台/灯光都在动。
      抽 24 帧算**逐像素时间极差** → 取"几乎不变"的像素 → 横向前景连通 →
      候选块按 `bug_glyph_score`（**像不像一排白字**：块数 ≥10、块高中位 ≥8px、
      白块挤在同一条文字行上）排序。实测全画面只剩**一个**稳定连通块，
      就是台标 `(202,56,562,27)`（人工真值 198,56,570,24）。
      颜色/几何那条路保留为回退，两者都不成立才如实说"没有比分牌"。
    - **OCR 只认那一块并放大 4 倍**：老代码 OCR 整帧，读不出 12px 高的比分数字
      （这段素材直接返回 None）。实测放大后同一套 Windows OCR 稳定读出
      `KPHS 27 / AHS 35`，48/48 帧全中。
    - **解析按版式配对**：老解析要求队名 Token ≥4 个字母，`AHS` 被丢掉 →
      两个比分都配到同一个数字，读出 **27 : 27**（真值 27 : 35）。
      新增 `_parse_pairs`：每个比分数字配它**左边**最近的词，并排除节次标记。
    - 结果：这一段读出 **27:33 → 27:35 → 27:37 → 29:38**，与画面逐帧一致
      （人工从 5 个时间点的截图核对过）。命令行/接口也可以手动框选兜底：
      `POST /api/scoreboard/ocr`（`box` 归一化坐标 + `start` 起始比分）。

15. **默认计分口径改成 `auto`**：比分牌**真读出来了**就用它（带入分 + 得分事件），
    否则按场上进球计分。为什么要改：这段素材画面写着 27:35，老默认口径输出
    **0:0** —— "分析结果和画面对不上"是用户最不能接受的错法。
    `game.carry_counted` 明确记录带入分到底算没算进总分，战报/摘要/前端都看它，
    不再各自去猜 `score_policy` 的含义。

16. **战术层的限制**（B 特有，写清楚）：
   - 控球判定依赖球轨迹连续性：球在空中只有 1 秒左右，`--player-stride` 可以抽帧，
     但**球追踪必须逐帧**；球轨迹覆盖率低时传球网络会偏空，`tactics.json` 的
     `notes` 里会写明。
   - 阵型识别是启发式规则：2-3 与 3-2 在球员移动的过渡帧上确实难分，
     所以返回的是「时间段 + 置信度」，请当参考值而不是绝对标签。
   - 只有位置信息时拿不到转身/背身这类姿态，进攻形状只报到「几外几内」，
     不硬编「低位单打」这种战术名词。
   - 球员身份仍是「主/客 + 跟踪 ID」（球衣号 OCR 未做），传球网络的节点名字
     是「主队3号」这种；换人后 ID 会变。
   - **真视频链路已端到端跑通一次**（见下面第 17 条），但**不同素材差异极大**：
     先跑 `python scripts\probe_footage.py --video <视频>` 做体检，再决定口径。

17. **真视频端到端实测（本机，2026-09-22）**：
   `data/uploads/35eaedfbaa6bd9d2046c6f3845638924_852dedd747.mp4`
   （4 分钟、960×544 校园转播，手标过篮筐）：
   - ✅ **比分读对了**：自动定位（叠加层稳定性）→ 只 OCR 那一块并放大 4 倍 →
     读出 27:33 → 27:35 → 27:37 → 29:38，与画面逐帧一致（48/48 帧命中）。
   - ❌ **战术图不出 —— 这是正确的结果**：该素材的静态标定点位退化被拒
     （篮筐被投到 33.4m 外），自动逐帧标定又**没过独立校验**：手标篮筐经它投影后

     `tactics.json`，`game["tactics"]["reason"]` 直接写出这句读数。
     修法：手工重标这个机位（同一帧里点 6 个以上、不在同一条线上的特征点）。

## 二、结论先说

1. **没有任何一个项目"装上就提准确率"**。这些仓库里没有篮球专用的球/篮筐权重，
   TrackNet 官方权重是羽毛球，KaliCalib 依赖 mmcv/mmpose 且权重未随仓库提供。
2. **本轮最有价值的发现不是"某个模型"，而是一个实测出来的架构判断**：
   我们真正的瓶颈是**逐帧篮筐/球场几何精度**，不是球检测器。
   证据：球检测器在 fixedcam 19.1s 那一球上**完整跟住了穿筐前后的轨迹**；
   而同一个球，用"常量篮筐"算是擦筐（gx=−0.84），用"逐帧篮筐"算是穿过筐心（gx=−0.34）——
   **16 像素的篮筐位置误差就能把"进"翻成"擦筐"**，而 nathan 的篮筐在 27 秒里
   cy 漂了 38px、cx 漂了 39px。
3. 三个可以真正落地的东西（按性价比）：**①逐帧几何（P0）②球轨迹空洞修补（零成本，P1）
   ③把球轨迹接进判进球（P2，已有原型验证）**。

## 三、我做的离线原型与实测数字（本轮核心产出）

### 3.1 证据密度：为什么"篮下判进球"会饿死

从两段素材已保存的逐帧诊断里数出来的（脚本 `aihoop\_tmp\trace_density.py`）：

| 素材 | 帧×篮筐记录 | 有候选块 | 完全没有运动连通域 | 有块但被尺寸/形状过滤掉 |
| --- | --- | --- | --- | --- |
| fixedcam | 703 | 108（15%） | **503（72%）** | 58（8%） |
| dairy | 1670 | 304（18%） | 311（19%） | **1055（63%）** |

同一段素材里球检测器给出的候选点：fixedcam 591 个、dairy 639 个。
也就是说：**球检测器的证据量是帧差小方块的 2~5 倍**，而我们在判进球时只用了后者。

### 3.2 球检测器其实看得见那一球

`aihoop\_tmp\probe_ball_near_rim.py`，在 hoopsight 丢掉证据的那一帧附近：

```
fixedcam 19.1s（篮筐 (620.7,180.5) rx=17.9）
  19.10 (591.3,150.6) conf 0.85   gx=-1.64 gy=-1.67  ← 近筐
  19.13 (603.0,161.1) conf 0.92   gx=-0.99 gy=-1.08
  19.17 (613.5,171.3) conf 0.66   gx=-0.40 gy=-0.52   ← 平面上方 0.5 个圈半径
  （19.17→19.57 之间球被网挡住，检测器丢 0.4s）
  19.57 (619.9,213.2) conf 0.59   gx=-0.05 gy=+1.83  ← 平面下方 1.8 个圈半径
  19.60 (617.0,216.5) conf 0.86   gx=-0.21 gy=+2.01
```

球从上方穿到下方、横向一直在圈内、落点在平面下方 1.8 个圈半径 —— 
**这一球的证据是完整的，只是 hoopsight 那条帧差路径看不到它。**

### 3.3 原型：只用「球检测器 + 篮圈半径几何」数穿筐事件

脚本 `aihoop\_tmp\proto_ball_rim_events.py`。做法：球检测器候选 → 用**篮圈半径 rx**
归一化（不再用 ry）→ 找「球心从平面之上（≤−0.35）穿到平面之下（+0.5~+2.0）、
横向在 0.9 圈半径内」的事件，时间窗 0.8s。篮筐位置取已保存的逐帧位置
（没有 trace 的素材退回 `hoop.samples` 线性插值）。

| 素材 | 人工真值 | 现有产线（blob 路径，已含队友的容差修正） | 本原型（球轨迹 + 几何） |
| --- | --- | --- | --- |
| fixedcam | 3 进 / 4 不中 | 3 进（5.5 / 19.2 / 22.5） | **3 进（5.33 / 19.03 / 22.33），4 次不中零事件** |
| dairy | 3 进 | 2 进（17.1 / 26.0） | **3 进（6.27 / 16.73 / 25.73）** ← 多找到的 6.27s 那一球此前两条路径都没发现 |
| nathan | 5 进 / 1 不中 | 7 出手 4 进 3 未知 | 5 个真进球全中 + **1 个额外（10.55s）** |

那个 nathan 的额外事件值得单独说（它同时暴露了问题与机会）：

```
球轨迹（ball_tracks_dump.json，nathan）：
  轨迹#0 末端 t=10.71 (527.2,151.1)
  轨迹#2 起点 t=11.15 (527.1,185.3)   ← 0.44s 后同一横向位置、下落 34px
用常量篮筐(553,154,rx=31)：gx=-0.84 → 判成"擦筐掠过"（我们的 rim_inner=0.85 边界）
用逐帧篮筐(≈537,158,rx=29)：gx=-0.34 → 判成"穿过筐心"
```

**同一颗球、同一段轨迹，结论取决于篮筐位置那 16 个像素。** 这不是球检测的问题，
是几何的问题。

### 3.4 出口判据的离线 A/B（证明方向不是过拟合）

`aihoop\_tmp\proto_exit_rule.py` 复刻了 hoopsight「找入筐点→找出筐点」这一步，
先在 baseline 模式复现真实产物（fixedcam 得 {5.4, 22.4}、dairy 得 {16.93, 25.83}，
与线上产物逐条一致 → 复刻可信），再比较几种出口判据：

| 出口判据 | fixedcam 事件 | dairy 事件 |
| --- | --- | --- |
| 现有：球心低于 `1.0×ry` | 5.4、22.4 | 16.93、25.83（+篮筐#1 一条） |
| 队友已实现的容差（≤0.5px 且 ≤0.1ry，横向 ≤0.6rx） | 5.4、**19.1**、22.4 | 同上，无新增 |
| 提议A：纵向门槛改成 `0.2×rx`（≈4.5cm） | 5.4、**19.1**、22.4 | 同上，无新增 |
| 提议B：纵向仍用 ry，但允许≤0.15s 的轨迹外推 | 5.4、**19.1**、22.4 | 同上，无新增 |

**三种改法都能找回那一球，且在 dairy 上都不新增事件** —— 说明这个修复不依赖
具体调参，而是"把绝对像素门槛换成物理尺度"的方向本身对。（顺带说明：我上一轮建议的
`max(ry,4~6px)` 方向是错的，那会**提高**薄筐的门槛；队友拒绝它是对的。）

## 四、三个仓库的代码级结论

### 4.1 TrackNet 系列（子代理 A，报告：`_refs\reports\A_tracknet.md`）

* **表示**：热图回归，无检测框。输入 `(B, 9~27, 288, 512)`，输出 `(B, L, 288, 512)` 的
  sigmoid 热图，阈值 0.5 后取最大连通域质心解码。标签是半径 2.5~3px 的二值圆盘。
  输出天然在原始像素系（letterbox + 反算），**能直接对接我们 `ball.py` 的像素门限**。
* **关键量级**：篮球在 512×288 输入下半径 2~4px，与官方羽毛球标签半径同量级 →
  标签/分辨率几乎不用改；真正要改的是域（篮网遮挡、夜间、手持机位）。
* **抗遮挡四招**：时序堆叠、中心加权时序集成、中值背景通道、轨迹级 1D inpaint 修正
  （判据：前后两次检测都在画面高处且 δ=30px、mask_ratio=0.3、轨迹长 16）。
* **不能直接用**：本机两仓库**都没有预训练权重**；官方权重是羽毛球；V1 网球模型直接
  跑羽毛球召回仅 22.9%（跨运动迁移有负面实测）；TrackNetV3 钉 torch 1.10、
  25 处硬编码 `.cuda()`，与我们环境冲突；许可无法确认（README 称 MIT 但仓库缺 LICENSE 文件）。
* **最值得做的一件（零成本）**：把 inpaint/线性插值补点搬进 `ball.py` 的
  `stitch_tracks` 之后，给补出的点标 `source="interp"` 并降 score。验收标准：
  判进数只能升不能降、**不得新增假进球**（我们目前是零误报）。

### 4.2 KaliCalib（子代理 B，报告：`_refs\reports\B_kalicalib.md`）

* **它是什么**：单帧独立配准。ResNet18+U-Net 输出 **94 路热图**（91 个地面点 + 2 个篮筐点 +
  1 个背景，13×7 网格），质心解码后 `cv2.findHomography(RANSAC, 35px)` **一次**解出地面单应，
  再用 `cv2.calibrateCamera` 转成相机矩阵 P。
* **不支持移动机位**：全仓 `video / kalman / smooth / track` 零命中，**没有时序、没有 refine、
  没有线约束** → 它治不了我们"手持机位"那个痛点（那需要逐帧/时序配准）。
* **权重没有随仓库提供**（`models/`、`dataset/` 是空目录）；无 LICENSE 文件，
  README 称 CeCILL-2.1（强著佐权）；精度 107.78/73.16 mm **只在地面 z=0 上验证过**，
  9ms/帧（1080Ti）。依赖 `deepsport-utilities`，在我方 Python 3.13 + torch 2.14 下
  能否安装未验证。

**但它带来三个比 KaliCalib 本身更值钱的发现（我已逐条核过代码）：**

1. **`ry` 的退化被解释清楚了**：`ry` 是篮圈在**视向方向**上的像素尺度，篮圈接近正侧视时
   它 → 0。我们手标的薄筐 `ry=3.9px` 就是这个退化 —— 所以"出口差 0.16px"这类问题
   **不需要 KaliCalib 就能修**：用篮圈半径（0.225m）或篮板高（1.05m）换算像素/米即可。
2. **我们仓库里已经有一条纯球场坐标的穿筐判据，但在真实视频上**永不触发**：
   `rules.detect_rim_events`（`rules.py:210`）的判据是"水平距离 < 0.25m 且高度由 >3.05m
   下落到 <3.05m"，是完全几何、免训练的兜底路径；可是真实视频路径里
   `BallSample.z` 被**硬编码成 1.2**（`ball.py:578`、`sources.py:700/716/1354`），
   球高永远是 1.2m，**这条判据一次都不会成立**（只有合成数据上活着）。
   缺的不是判据，是**相机模型 P**。
3. **"单目也能判穿筐"在数学上成立**：单目下球的高度不可观测，但"球心射线 ∩ 已知平面
   z=3.05m"是唯一确定的 ⇒ 只要有了 P，就能把穿筐点投到 3.05m 平面上去判 0.225m 的圆，
   **不需要球的三维位置**。这正好把我们第三节 3.3 那个"16px 篮筐误差就能翻盘"的问题
   从"像素阈值"变成"米制几何"。

### 4.3 五个「投篮分析」仓库（子代理 C，报告：`_refs\reports\C_shot_repos.md`）

先说总结论：**这 5 个项目没有一个用分类器判进球**，判据都是「像素规则 + 一两帧轨迹几何」，
而且**普遍比我们的 `hoopsight._judge_span` 弱**：它们没有筐内证据帧、没有下落距离、
没有回弹否决；`ball-yolo` 甚至退化成"球出现在筐下方区域就算进"。
**回放球与补篮 5 个项目全都没处理**；擦筐只有我们做了（`cup_inner=0.62` + `min_cup_frames=2`）。
全部**零真值评测**，`ball-yolo` 的 WORKFLOW 自称"检出率>95%"没有任何数据支撑。
**5 项许可全部无法确认**（全树无 LICENSE），且它们都依赖 Ultralytics（AGPL-3.0）——
抄思路可以，抄代码/权重对闭源产品是红线。

唯一值得抄的是 `basketball-tracking` 的**事件层工程纪律**（它自己的进球判据很弱，
但周围的护栏极强），三条：

1. **证据来源白名单**：`core.py` 里 `ball_state_counts_for_events` 只允许
   `yolo / csrt / user / tiled / roi` 这些**实测**来源为事件作证，`kalman / interp / color`
   一律排除，并用回归测试把契约钉死。
   → 落到我们：现在的 `exit_tolerance_used` 只写进 trace（诊断用），应该**升级为逐点标签**
   传给 `_judge_span`，容差档证据要**扣置信度**，并且"只有容差证据"时给出机器码
   `exit_tolerance_only` —— 这样那两类漏判/边界球在 `candidate_trace["counts"]` 里能直接看出原因。
   同一个原则也适用于 `allow_hole_interpolation`：**它继续默认关闭是对的**。
2. **相机运动补偿**：`core.py` 用 ORB+Shi-Tomasi+LK 估计逐帧单应，
   **先用运动掩膜把移动物体（球员/球）剔掉**，内点 <8 或尺度变化 >0.12 就沿用上一帧。
   → 落到我们：`hoop.py` 的 `max_drift_frac=0.22` 现在是**硬否决**（夜间手持那段就死在这条上）；
   应该改成**作用在补偿后的残差**上；`hoopsight._hoop_at` 现在"最近采样 ≤2.0s 才用采样，
   否则退回中值"——手持素材 2 秒空档很常见，应该改成"最近采样 + 用累计变换搬运到 t"。
   这正好接上第三节 3.3 的实测结论：**篮筐位置 16px 误差就能翻盘**。
3. **素材可判性诊断 + 送人工抽检**：`diagnose_ball_visibility` 返回球可见率与**逐来源计数**；
   `suggest_ball_interp_check_frames` 挑出必须人工确认的帧。
   → 落到我们：我们的 `_judge_diagnosis` 方向对但只有 1 个维度，应该扩成诊断表
   （`candidate_frame_rate`、`blob_stats` 里 `area/exp_area` 的 p50/p95、`exit_measured_ratio`、
   补偿后的残差），并给"靠容差得来的进球"生成人工复核图。

**最危险的反模式（值得写进我们的规则里）**：`nba-analysis-yolo` 把 174 帧里 **139 帧
（79.9%）的球坐标用插值伪造**（`interpolate` 加 `bfill`），然后照样在假轨迹上判事件。
这就是我们坚持 `allow_hole_interpolation=False` 的最好理由。

**数据集线索（我们最缺的东西）**：`Basketball-51dataset` 的 README 指向一个含
**8 类 make/miss、10,311 段真值视频**（6 秒 / 320×240，Kaggle + gofile）的第三方数据集，
许可未声明、需人工确认。这是我们目前最缺的"独立真值素材"来源。

## 五、建议的路线（按性价比）

1. **P0｜把"篮筐平面"从像素门槛换成球场坐标几何**（对应第三节 3.3/3.4 与第四节 4.2）。
   两条路，建议先做便宜的那条：
   * **P0-a（约 20 行，无新依赖）**：用**篮板高 1.05m**（或篮圈半径 0.225m）反算
     世界竖直方向的像素/米，把 `hoop.py` 里 `min_cross_drop_frac × ry` 这种"像素倍数"
     门槛换成**米制阈值**。直接修掉"薄筐 0.16px"这一类。
   * **P0-b（要一点几何工作）**：给 `court.Calibration` 加可选的相机矩阵 P
     （准入闸门用"已知 3D 篮筐 (0, ±1.575, 3.05) 的重投影残差"），然后把球心射线
     投到 z=3.05m 平面上判 0.225m 的圆 —— 这会让仓库里**已经写好但永不触发的**
     `rules.detect_rim_events`（`rules.py:210`，判据是 0.25m / 3.05m）在真实视频上活过来，
     顺带修掉"横向 0.10rx"。
   * 同时把 `HoopTrack` 的采样存全（现在 `to_dict` 只存 `samples[::5]`），
     `hoopsight._hoop_at` 改成"最近采样 + 累计变换搬运"，`max_drift_frac` 的硬否决
     改成作用在**补偿后的残差**上 —— 这几条一起治"手持机位直接放弃"。
2. **P1｜球轨迹空洞修补**（TrackNet 的 inpaint 思路，零权重零训练）。
3. **P2｜把球轨迹接进判进球**（第三节原型：fixedcam 3/3、dairy 3/3、nathan 5/5+1 待定）。
   这条路的精度上限由 P0 决定 —— 先做 P0 再决定要不要替换 hoopsight。
4. **不建议**：直接引入 TrackNet 权重（没有篮球权重、许可不清、环境冲突）；
   直接抄那些"投篮识别"仓库的判定逻辑（多数没有真值评测，判据比我们弱）。

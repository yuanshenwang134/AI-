## 一、做了什么

### 1. 独立候选层（`src/aihoop/legacy_shots/stream.py` 里的 `shot_candidates`）

**纯事后统计**：跑完一遍后，从已录的逐帧依据（真实球观测 + 当时的筐位）里找轨迹形态，
**不进入 `ScoreEngine`、不产生事件、不影响任何判定**。规则（与上一轮原型验证过的口径一致）：

1. ±0.6 秒滚动窗口找局部顶点（y 最小 = 最高点）；
2. 顶点前上升 ≥ 25px、顶点后下落 ≥ 12px；
3. **该段轨迹曾接近篮筐**（到筐心最小距离 ≤ 3×筐宽）——注意不是"顶点接近筐"（跳投顶点离筐很远）；
4. 1.2 秒内去重，留上升最高的那个；
5. 按"弧线起点离筐心的距离"分类：`< 3.5 筐宽` = `near`（补篮/二次进攻/打铁反弹类），
   否则 `far`（远投类），框位缺失时 `unknown`；
6. 另补 `vanish` 类：上升后球消失（对应飞出画面/被遮挡）。

每条候选给出：`release_t`（出手时刻，回看时间 = 它前 1 秒）、`apex_t`、`kind`、`rise_px`、
`fall_px`、`obs_frames`、`start_dist_rims`、`klass`。**没有 `made`/`result`/`points` 任何计分字段。**

阈值放在配置里（`DEFAULT_CONFIG['detect']`，会随模型指纹一起落盘）：
`cand_window_s` / `cand_rise_px` / `cand_fall_px` / `cand_near_rim_widths` / `cand_dedupe_s` /
`cand_close_start_widths` / `cand_max`(40)。

### 2. 球可见性摘要（同文件的 `ball_visibility`）

与已有的"可用筐时段"并列：`observed_frames` / `sampled_frames` / `observed_fraction` /
`blind_ranges`（连续 ≥2 秒没有任何**真实**球观测）/ `longest_blind_s`，
并带一句 `note`："按真实球观测统计；predicted 帧不计，缺证据不等于没有投篮。"

### 3. 落盘与界面

| 位置 | 变化 |
|---|---|
| `raw_track.json` | 新增顶层 `detections_meta.legacy_shots.shot_candidates`；`rim_tracking` 里新增 `ball_visibility` |
| `game.json` | `meta.shot_engine_details` 增加 `shot_candidates`（`pipeline.py` 的精简选择里加了一个键） |
| 总览页（`overview.js`） | 新增卡片 **「待核对的轨迹候选」**（修订后名称）：写明"仅提示，不计入出手次数与命中统计"、逐条给"回看 hh:mm"按钮（跳到出手前 1 秒）、形态与分类，并**标明与已有事件的关联**（"与已有事件时间接近 / 未对应任何事件"，未对应的排前面）；卡片内再分出一块 **「另 N 条「证据跨段」」**（`cross_segment`，单独计数、不计入上面的条数）；覆盖卡片里补一行 **球检测观测率** + 盲区时段回看按钮 |
| 缓存版本 | `overview.js?v=38-crosssegment` |

**落盘核验（走产品路径，不是离线脚本）**：改了 `stream.py` 后由 `serve_reload.py` 自动重载，
用 API 重跑 day 片段（job `b60013ddbc56`，48 秒完成），读 `game.json` 得到
`shot_candidates.count=9 / unmatched_count=4 / cross_segment_count=1`，跨段条目为
`10.177s, arc, blocks_in_window=3, matched=True`，与离线计算逐项一致；球检测观测率 38.9%。
即**新字段确实经 `pipeline.py` 写进了新任务产物**。

**判定路径一个字没改**：`events`、`timeline`、比分、建议（`suggested_made`）全部按原样。

### 2.1 断段保护改变了什么（**这一节此前结论错误，2026-09-30 重做**）

先说错误：我上一版写"断段保护在这六段真实数据上没有改变任何候选（day 10→10、night 9→9）"，
并把它说成"结构性保险"。**这个验证方法本身是错的**——我是靠"把 `cut` / `evidence_segment` 字段
从 trace 里 pop 掉、再把 `tracked_rim.segment` 改成 1"来模拟"没有断段"的。
但缺字段的帧会落回 `(None, None)`，与被改成 `(None, 1)` 的帧**交替**出现，
于是每一帧都成了新段——那是另一种病态分段，而不是"没有断段"。
那次测出来的"没有变化"，是方法缺陷造成的假阴性。

**正确做法**：把所有帧强制成同一段（`cut=False`、`evidence_segment=1`、
并且对缺失 `tracked_rim` 的帧也补上 `segment=1`，不再让 `None` 参与比较）：

| 素材 | 有断段（现行口径） | 强制同一段 | 差别 |
|---|---|---|---|
| `day_outdoor` | 9 | 10 | 多出 **10.177s**（顶点 10.677，arc，上升 137px） |
| `night_outdoor` | 9 → **9**（现行口径 8） | 9 | 多出 **14.014s**（顶点 14.381，arc，上升 159 / 下落 176px）与 **15.482s**（vanish） |
| `game01_seg45` / `fixedcam` / `dairy` / `nathan` | — | — | 无差别 |

也就是说：**断段保护确实在真实数据上去掉了 3 条候选**（day 1 条、night 2 条），
且这 3 条都紧贴切镜时刻（day 10.38s、night 14.38s）。逐条查清它们被去掉的原因（不是猜的）：

- `day 10.177`（顶点 10.677）：顶点落在切镜**之后**那一帧所属的段里（该段从 10.38s 起），
  段内上升只剩 43px，且段内的球点离筐都在 3 个筐宽之外 → 撞上"从未接近过筐"这条判据被拒。
  它跨段的口径下上升 137px、起点距筐 2.1 筐宽，看着像一条完整弧线。
  **但它与已有事件 13.61s(uncertain) 的离手时刻相差 1.43s**，是否同一次出手同样只能靠目视。
- `night 14.014`（顶点 14.381）：顶点**恰好是切镜后的第一帧**，段内上升段只有它自己（0px < 25px）→ 被拒。
  跨段口径下上升 159px、下落 176px、26 帧、**离手时刻附近没有任何事件**。
  **我当时把它写成"最像被切镜从中间截断的真实出手"——这句已被目视结果否掉**（2026-09-30）：
  画面显示 13.81–14.28s 是前一进攻结束后的篮下活动、14.38s 之后换成红 20 号运球推进，
  两边是**不同镜头里的不同活动**，没有连续出手证据。保留"跨段"警示，但**不得自动合链**，也不得
  据此宣称"找回了被切镜吃掉的出手"。
- `night 15.482`（顶点 16.049）：现行口径下顶点 15.282 的候选以 14.715s 存活，
  这条 15.482s 的 vanish 与它相差 0.767s < 去重间隔 1.2s → 被**去重合并**（保留上升更大的那条）。

**game01 的段边界不是切镜造成的**：该片段 `cut` 为 0 处，段边界来自跟踪段变化
（`evidence_segment` / 篮筐跟踪段）。所以这一层的字段名用 `cross_segment`（跨段）而不是 `cross_cut`。

### 2.2 新增：证据跨段的候选单独列一层（不改主列表）

既然"被排除"不等于"不存在"（用户要求：不能把看不清/没看到证据的时段当成检测完整），
就按不受段限制的口径再算一遍，把**主列表里没有的顶点**作为独立一份列出来：

- 新增字段（同一份 `shot_candidates` 里，**单独计数**）：`cross_segment` 列表、
  `cross_segment_count`、`cross_segment_truncated`、`loose_only_same_segment`（多出来但没跨段、
  即被去重合并掉的那类，只报个数不重复列出）；每条跨段候选带 `cross_segment` 布尔与
  `blocks_in_window`（证据横跨几段）；
- **主列表的条数、顺序、判定关联一个字没动**：六段逐条比对改动前后完全一致
  （`count` / `unmatched_count` / 每条 `release_t,apex_t,kind,rise_px,fall_px,matched` 全部相同）；
- 实测这 3 条：`game01 2.135s`（与已有事件时间接近）、`day 10.177s`（时间接近，差 1.43s）、
  `night 14.014s`（**未对应任何事件**）；
- 界面：候选卡片里多一块「另 N 条「证据跨段」」，写明**单独计数、不计入上面的条数、也不计入
  出手次数与命中统计**；主列表为空而只有跨段候选时卡片也要显示（`index.html` 版本号 `?v=38-crosssegment`）。

候选数与上一轮原型（用离线脚本算的）量级一致：day 9、night 8、fixedcam 9、nathan 8、dairy 6、game01 7。

**但要说清楚"证明了什么、没证明什么"**：六段回归证明的是**它没有改变现有判定**（序列/比分/事件逐条一致），
**没有**证明"它实际找回了哪些漏投"——那需要逐条回看画面（我看不到图）。
候选里"未对应任何事件"的条数（day 4、night 7、game01 3、nathan 2、dairy 2、fixedcam 1）是
**待回看的清单**，不是"找回的漏检数"。

**待目视的具体时刻已整理成可填表**：`docs\轨迹候选目视核对_待填_2026-09-30.md`
（含每个时刻的形态、上升/下落像素、观测帧数、与已有事件的时间差、该时刻篮筐是否在画面里，
以及三个核对包目录 `out\<job>\review_shots_20260930\`，每个时刻有 8 帧拼图与前后 7 秒短片）。

### 2.3 目视结果（AI 目视草稿）与它引出的三个失效模式

**目视结果不是人工真值**：13 条候选的结论是 **4 条真实投篮动作 / 8 条非投篮 / 1 条无法可靠归属**
（night 的 3.337s 我先前漏放，尚未目视，所以不是全量 14 条）。逐条结论见上述核对文档。
其中两点直接影响候选层的定位：

- `night 14.014s` 这条跨段候选**不是**"被切镜截断的真实出手"（两边是不同镜头的活动）——
  我上一版文档里的那句话已更正；
- `day` 目视确认的两次出手动作（候选顶点 19.152 / 21.154）**都不在**该片段只有 3 条的真值里，
  也就是"真值是否完整"要人工定，**我不改真值、也不据此改统计**。

**由目视发现的三个失效模式**（详情与完整数据见 `给GPT的说明_候选身份与篮筐失效_2026-09-30.md`）：

1. **球框误认人/头**（night 20.621）：真检测球框是 97–111 × 144–159px 的竖长框，
   而该片段有效筐宽只有 51–54px；全片竖长框占比 fixedcam 0% / day 5% / night 14%。
   但真实投篮窗口也有 28–40%（day 18.819、night 16.850/20.621），所以**它只能当证据质量标记**。
2. **持球走动产生候选**（night 24.458/27.995、day 16.183）：球心落在人体框内的比例达
   92% / 100% / 90%，而"最长连续球在人框外"只有 2 / 0 / 2 帧（真实出手是 10~18 帧）。
   判据候选"连续人框外 ≥8 帧"在 11 条标注上仍错 2 条，**不是投篮分类器**。
3. **篮筐可见却未跟踪**（night 16.850）：夜间全片有效筐只有 4 段，14.35–31.36s 整整 17 秒没有有效筐；
   用产品同一权重实测该时刻筐类 **conf = 0.000（模型完全没输出）**，而有效筐段是 0.74–0.81；
   `imgsz` 640→960/1280 能把已知筐的 conf 从 0.26 抬到 0.50+，但救不了 16.85s 这一处。

**因此本轮给候选层加的是"证据描述"，不是新的过滤器**（主列表条数、顺序、事件关联一个字未动）：
每条候选新增 `ball_obs` / `ball_box_w_med` / `ball_box_w_ratio` / `tall_box_frac` / `in_person_frac` /
`outside_person_run` / `cut_truncated` / `evidence_flags`，摘要给 `evidence_flag_counts`；
**窗口口径 = 顶点前后各 0.6 秒**（与候选判定同窗口，不是离手时刻 ±0.6s）。
没有球员检测时 `in_person_frac` / `outside_person_run` 为 `null`（**未知，不是"否"**）。
界面上写成「证据提示：…」并明确标注**"这不是投篮与否的判定"**。

**`cut_truncated`（证据被切镜截断）的判据要同时满足两条**（缺一条就会误报，都是实测踩出来的）：
① 这条候选自己的证据点**就是该段里最后的球观测**；② 切镜紧接其后（≤0.5s）。
只用窗口边界会误报（day 26.86s 那条完整弧线被误标），只用"该段最后一次球观测离切镜近"会泛滥
（day 一次标出 8 条）。实测最终命中：**day 只有 4.004s 与 18.819s**，其余影片 0 条。

### 2.4 "先看进球、再看出手"这条路线的核实结果

复核方提的思路（先找球穿筐、再回头找离手动作）**引擎里已经实现**，即事件的
`evidence_grade=measured_crossing` 与 `crossing_t`：`nathan` 6/6 条事件带 `crossing_t`（含 5 次 make）、
`fixedcam` 3 条（正是真值的 3 次 make）、`night` 1/1 条、`day` 2 条。
我自己写的朴素"相邻帧球检测横跨筐心"扫描只扫到 0~1 次 —— 说明**不需要另写一个结果优先检测器**，
引擎现有的这一路更强。

**值得改的是信任度判定**：`day` 的 `crossing_t=12.646` 对应人工真值第 2 球（`rim_s=12.45` 的 make），
但该事件因落在 `below_rim_tracking_gap` 被降级成 `uncertain` —— 这次 make 的信息**已经在产物里**。
建议把"测到穿筐"与"筐在空档里"分开表达（如 `crossing_measured` + `crossing_confident`），
而不是把整条判成 uncertain。

**同时明确不做的事**：不把切镜两侧的轨迹**自动接起来**判结果 ——
`night 14.014s` 那条跨段弧线（上升 159px、下落 176px、26 帧）经目视确认是两个不同镜头的不同活动，
自动合链会造出一次不存在的出手。跨段只保留"警示 + 单独计数"。

## 三、边界（不夸大）

- 候选**不是"漏掉的投篮"的证明**，只是"轨迹像投篮"的提示；`matched=true` **只表示离手时刻与某条
  已有事件在 1.5 秒内接近**，既不证明是同一次出手，也不能推断成"打铁后的反弹/同一球的后继"；
  哪些是真投篮、哪些是传球/运球/捡球，**必须回看画面**（本机看不到图）；
- `cross_segment` 里的候选**证据不完整**（上升段与顶点分属两段），既能是"被切镜截断的真实出手"，
  也可能是"两段画面各自的动作碰巧接成了一对"。它只是**不再被静默丢掉**，不代表它更可能是投篮；
- 阈值（25px 上升、±0.6s 窗口、3 筐宽、1.5s 关联容差、1.2s 去重等）是按这 6 段开发素材调的，
  **没有独立素材验证**；去重间隔还会改变"哪一条顶点存活"，因此贴边的计数（如 night 的 14.7 / 15.48）
  换个阈值就会变，不宜当成稳定指标；
- `fixedcam/nathan/dairy` 只有顺序真值（无时刻），所以"候选里有几个是真投篮"无法量化；
- 球检测观测率（如 night 29%）**不等于录像可见率**：没检测到可能是检测器漏检；
- 旧任务需**重建产物**才会出现候选、球可见性与跨段字段（旧产物里没有 `cross_segment`，
  前端会安全地按"没有这块"渲染）；
- 本轮**没有**改动判定、比分、默认实验开关，也**没有**把候选（含跨段候选）写进任何统计。

## 1. 先统一坐标系（这一步不做，后面全错）

整条链路（标定 → 计分 → 热区 → 战术）只允许存在**一套**球场坐标：

```
x 横向 ±7.5（x = 0 是球场中轴；|x| 越大越贴边线）
y 纵向：符号表示"在哪半场"，|y| 表示"离本方底线的距离"
        |y| = 0 是底线，|y| = 14 是中圈
篮筐 (0, ±1.575) —— 1.575m 正是 FIBA 规定的"篮筐圆心距底线"
```

战术层在这个基础上再定义一个**局部进攻坐标**：

```
(x, d)  其中 d = |y|
→ 被进攻的篮筐永远是 (0, 1.575)，左右两侧的进攻可以直接叠在一起比较
→ 前端俯视战术图只需要画「一张半场」：u = x + 7.5、v = d
```

> 局部进攻坐标由 `attack_frame()` 完成，是阵型识别与空间指标的共同基础。

### 1.1 这里发现并修掉了一个真实 bug（答辩可以当亮点讲）

老版本的半场标定点 `HALF_COURT_CORNERS` 把**底线**映射到 `y = -14`、
**中线**映射到 `y = 0`，但计分引擎、热区网格、前端 `court.js` 全都认为
`|y| = 0` 是底线。两套口径差了整整 14m，后果是：

* 篮下上篮被算成「离篮筐 12.4m」→ **规则引擎判成三分**；
* 俯视战术图整体偏移 14m —— 而且图看起来还挺像那么回事，**不报任何错**。

修法：`HALF_COURT_CORNERS` 改为 `(底线) y = 0 → (中线) y = -14`；
全场标定（`frame="full"`）保留未折半坐标，由 `fold_to_analysis()` 折到分析坐标；
所有取坐标的地方统一走 `Calibration.to_court()`。
回归测试：`tests/test_plan_b.py::test_calibration_layup_is_two_points`
（标定一台"虚拟相机"，投影篮筐必须回到 `(0, -1.575)`，篮下必须是 2 分）。

## 2. 算法：四步从"点位"到"战术"

全部在 `src/aihoop/tactics.py` 里，纯 Python（凸包、插值、分档都是自己写的），
不引入 numpy / sklearn —— 和 `court.py` / `rules.py` 保持一致，
最小依赖环境下也能跑完整条自检。

### 2.1 控球归属（`detect_possessions()`）

1. 每个球采样点找**最近的球员**，距离 ≤ `possess_radius`（默认 2.5m）才算他在控球；
2. 对"控球人"序列做滑窗多数投票（窗口 ≈ 0.6s），压掉单帧抖动；
3. 连续相同的控球人合并成一段，短于 `min_possession`（1.0s）的丢掉。

> 为什么用"最近球员"这么朴素的判据：它是**可复现、可视化、可逐条讲**的。
> 用一个训练出来的控球分类器，答辩时反而说不清"为什么这一帧算他控球"。

### 2.2 传球事件与传球网络（`detect_passes()` / `pass_network()`）

控球人从 A 换到 B：

* 同队 → **传球**（pass）
* 跨队 → **球权转换**（turnover / steal）

两处易踩的坑（都已修 + 有回归测试）：

* **不能用"两段球权之间的空隙"当过滤条件**：那个空隙是球员检测的采样间隔
  造成的（A 的最后一个采样点 → B 的第一个采样点），拿它跟 `pass_min_gap`
  比会把所有传球都误杀，而且抽帧越稀杀得越干净。正确做法是"先建事件、再按
  事件时间做去抖"。
* **球员位置查询必须允许"保持"首尾采样点**：传球发生在 A、B 采样点的缝隙里，
  不允许保持的话，判定传球时"传球人已经不在场"，传球全被丢掉。

传球网络：节点 = 球员（带平均站位 `x` / `d`），边 = 有向传球次数。

### 2.3 阵型识别（`classify_offense()` / `classify_defense()`）

**进攻落位**（按三分线口径数外线人数，与 `rules.is_three_pointer()` 完全同源）：

| 形状 | 判据 |
|---|---|
| 五外拉开 | 外线 5 人 |
| 四外一内 | 外线 4 人 |
| 三外两内 | 外线 3 人 |
| 双塔（内线为主） | 外线 ≤2 且内线（≤4m）≥2 |
| 均衡落位 | 其余 |
| 转换进攻 | 有人还在 `d ≥ 13`（接近中圈） |

**防守阵型**（两个正交判据，都写进返回值，方便逐条核对）：

* `man_gap`：每名**进攻**球员到"最近防守人"的距离均值 —— 人盯人时很小；
* 纵深分布 `top / mid / low`：按 **离本方底线的纵深 d** 分档
  （`d ≥ 5.5` 上线 / `3.0 ≤ d < 5.5` 中间 / `d < 3.0` 收缩在篮下）。

> 为什么纵深而不是"离篮筐距离"：底角三分点离篮筐也有 6.7m，
> 用离篮距离会把"站底角的防守人"误判成上线。

| 阵型 | 纵深形状 |
|---|---|
| 2-3 联防 | 上线 2、篮下 3 |
| 3-2 联防 | 上线 3、篮下 2 |
| 1-3-1 联防 | 上线 1、中间 3、篮下 1 |
| 1-2-2 联防 | 上线 1、中间 2、篮下 2 |
| 人盯人 | `man_gap ≤ 1.6m` 且凑不出上面的形状 |
| 前场施压（紧逼） | ≥2 人站在 `d ≥ 11`（接近中圈） |

判定优先级：紧逼 → 干净联防形状 → 人盯人 → 混合。
联防站位有时也会让 `man_gap` 变小（进攻方恰好站在防守人旁边），
但**纵深形状在整段进攻里是稳定的**，反过来真正的人盯人很难凑出 2-3 / 3-2 的形状。

### 2.4 空间指标（`spacing_metrics()`）

| 指标 | 含义 | 算法 |
|---|---|---|
| `area` | 凸包面积（m²） | Andrew monotone chain + 鞋带公式 |
| `mean_dist` | 两两平均距离（m） | O(n²)，n=5 无所谓 |
| `width` | 阵型横向宽度（m） | `max(x) - min(x)` |
| `depth` | 阵型纵深（m） | `max(d) - min(d)` |
| `radius` | 重心到被进攻篮筐的距离（m） | 重心 → `(0, 1.575)` |

凸包面积最直观："拉开了没有"。**注意抽稀的坑**：`spacing.timeline` 是
主客交替排列的，整体 `[::2]` 抽稀会与球队交替同频，结果只剩一支球队，
而且不报任何错 —— 必须**按球队分别抽稀**（`test_spacing_timeline_keeps_both_teams` 守住）。

## 3. 数据契约

### 3.1 `tactics.json`（完整战术结论）

```json
{
  "available": true,              # False 时 reason 里写清为什么
  "reason": "",
  "attack_side": "left|right|mixed",
  "coverage":   {"player_samples":..., "players":..., "ball_samples":..., "frames":...},
  "possession": {"total":..., "spells_total":..., "by_team":..., "avg_passes":...,
                 "avg_duration":..., "list":[...], "spells":[...]},
  "passes":     {"total":..., "turnovers":..., "by_team":..., "events":[...],
                 "leaderboard":[...]},
  "pass_network": {"home": {"nodes":[...], "edges":[...]}, "away": {...}},
  "formation":  {"offense": {"home":[...],"away":[...]},
                 "defense": {"home":[...],"away":[...]},
                 "summary": {"home":{"offense":[...],"defense":[...]}, ...}},
  "spacing":    {"teams": {"home":{...},"away":{...}}, "timeline":[...]},
  "insights":   [{"type":"pass|space|formation", "t":..., "text":"..."}],
  "notes":      ["..."]
}
```

> `possession.total` 是**回合数**（同队多次传导合并后），
> `possession.spells_total` 才是细粒度的控球片段数。
> 这两个数很容易混：一次进攻传 3 脚会产生 4 个控球片段，但只算 1 个回合。
> 不合并的话"回合数"会被传球次数放大好几倍。

### 3.2 `tactics_frames.jsonl`（俯视战术图逐帧数据）

一行一帧，供前端播放器渲染：

```json
{"t": 12.5, "side": -1, "ball": [1.2, -6.4],
 "players": [["H1", "home", -3.1, -5.2], ["A1", "away", 0.4, -3.9]]}
```

用 JSONL 而不是一个大 JSON：流式写、单行可读、崩了不会毁掉整个文件；
前端演示模式（无后端）由 `scripts/jsonl_to_json.py` 转成 JSON 数组。

## 5. 前端

新增第 8 个页面 `web/pages/tactics.js`（hash 路由 `#/tactics`），四块内容：

1. **俯视战术图播放器** —— 两层 SVG 叠放：球场层（`courtSVG({view:'half'})`）
   与球员层（`tacticsPlayersLayer()`）用**同一个 viewBox**，
   所以只要容器尺寸一致就能像素级对齐。带播放/暂停、进度条、倍速、轨迹尾迹。
2. **传球网络** —— 直接画在半场上（`passNetLayer()`）：节点 = 平均站位、
   圆内数字 = 传球+接球次数、连线粗细 = 两人之间传球次数。比用 ECharts 关系图
   更直观，而且和球场底图同一套坐标，不会出现"网络图和球场对不上"。
3. **阵型识别时间轴** —— 每段一个色块（宽度 ∝ 时长），点击跳到该时刻；
   上面的表格给出两队的主要进攻/防守阵型与出现次数。
4. **间距曲线** —— ECharts 折线，五档指标（面积/间距/宽度/纵深/重心距离）可切。

数据是**懒加载**的：只有真的打开战术页才去拉 `tactics.json` 与
`tactics_frames.jsonl`（30 分钟的逐帧数据接近 1MB），
不拖慢总览/统计这些高频页面。

## 8. 答辩口径（逐条对应可能的提问）

**Q：战术层是调了哪个开源库？**
A：没有。`tactics.py` 是纯 Python 自研，凸包/插值/分档都是自己写的，
零第三方依赖。判据全部是可解释的几何规则，不是训练出来的分类器。

**Q：传球网络的数据是怎么来的？**
A：球轨迹 + 球员轨迹 → 每个球采样点找最近球员定控球 → 控球人在队友之间
切换就是一次传球。传球事件再聚合成有向网络（节点带平均站位）。
两层都能可视化回放，可以对着一帧一帧核。

**Q：阵型识别凭什么说是 2-3 联防？**
A：两个正交判据写在返回值里：防守人的**纵深分布**（上线 2、篮下 3）
与**盯人紧密度 man_gap**。答辩现场可以直接把 `top/mid/low` 和 `man_gap`
调出来，指着数字讲为什么判成 2-3 而不是人盯人。

**Q：为什么俯视战术图只画一张半场？**
A：因为战术层把两侧进攻折叠成「局部进攻坐标」(x, d=|y|)，篮筐永远在 (0,1.575)。
一张半场就能同时表达左右两侧，而且两队可以直接叠着比较。
这不是省事，是有意的设计 —— 折叠之后"阵型形状"才可比。

**Q：这轮开发里最有价值的发现是什么？**
A：是**标定坐标系偏移 14m** 那个 bug。它不会报错、图也画得出来，
但篮下上篮会被判成三分、战术图整体错位。我们是在给俯视战术图接线时，
发现"篮筐投影回来不在 (0,1.575)"才揪出来的，随后加了回归测试
（`test_calibration_layup_is_two_points`）把它钉死。
这类"静默错误"是单目几何项目里最危险的一类。

## 9. 已知限制（写清楚比藏着好）

1. **控球判定依赖球轨迹的连续性**：球在空中只有 1 秒左右，抽帧就会连不成轨迹。
   所以 `--player-stride` 可以抽帧，但球追踪必须逐帧。
   球轨迹覆盖率低时传球网络会偏空，`notes` 里会写明。
2. **阵型识别是启发式规则**：2-3 与 3-2 在个别帧上确实难分（球员移动过程中会
   跨界），所以返回的是**时间段 + 置信度**，不是逐帧硬标签；
   置信度随"干净程度"变化，请当参考值而不是绝对值。
3. **转身/背身这类姿态信息拿不到**：只有位置时无法区分"低位单打"与"外线持球"，
   所以进攻形状只报到"几外几内"这一层，不硬编战术名词。
4. **球员身份仍是主/客 + 跟踪 ID**：球衣号 OCR 未做，所以传球网络的节点是
   "主队3号"这种名字；换人后 ID 会变，长视频的节点可能偏多。
5. **真视频未在本次环境中端到端验证**：本机没有可用的比赛素材与标定文件，
   战术层的真视频链路（投影球员框底部 → `player_track`）只做了单元级与
   合成数据级验证。请在答辩机上按 §6.3 跑一次并核对俯视战术图是否与画面吻合。

## 10. 真视频链路（**实测总结，不是设计稿**）

下面每一条都是在这台机器上用真实素材跑出来的数字，不是"理论上应该"。

### 10.1 单应标定只对固定机位成立 —— 有数据

| 素材 | 帧间位移 | 一份静态标定能撑多久 |
|---|---|---|
| 广播机位（`basketball_match.mp4`） | 4.0 px/s，含切镜（峰值 136px） | 8 秒的"同一镜头"里只有 **12%** 的帧达标 |
| 号称固定机位（`basketball_game.mp4`） | 2.1 px/s | 45 秒漂约 **90px**（底线还压在线上、边线已跑掉） |
| 手机手持片段 | 15.4 px/s | 单应方案**物理上不成立** |

> 只看"投影线有没有压到白线"会误判：**底线一直亮、边线早跑了**。
> 所以判定必须逐条线看，见 :func:`court_fit_score` 的 `lines` 字段。

### 10.2 逐帧滑动标定（唯一能跟住镜头的无模型方案）

`calibcheck.sliding_calibration()` 的三层成本控制：

1. **分数门控**：先花 ~3ms 量"当前角点还准不准"，准就沿用（实测 **74/90 个锚点走这条**，几乎零成本）；
2. **热启动精修**：分数掉下来才从上一组角点出发走小步长；
3. **重新锁死**：分数跌破阈值（镜头跳了/切镜）才做一次完整自动标定。

实测（15 秒广播片段，stride=5）：

```
锚点 90 个   中位 ratio 3.00   达标 100%
逐帧（插值后）中位 ratio 2.70   达标 98%
成本 ≈ 3.2 秒 / 秒视频
```

**成本换算**：15 秒素材约 50 秒；3 分钟素材约 10 分钟。整场 30 分钟要几小时 ——
要快到实时，只能上训练好的球场关键点模型（见 §12 的同款管线）。

### 10.3 球员和球必须用**同一套**坐标

踩过的坑：球员用逐帧滑动 H、球却用静态 H → 两者随镜头移动逐渐错开。
表现是**控球恒为 0、传球网络永远为空，而且不报任何错**。
修完之后控球片段 0 → 1（后续换用重训的球模型后到 8）。

> 教训：任何"多路证据融合"的系统里，**坐标系来源必须唯一**。
> 这类 bug 不会崩、只会静默地给出全 0，最难查。

### 10.4 球员检测的场内过滤与人数上限

广播镜头一帧能检出 **23~26 个 person**（球员+裁判+替补席+观众），
其中一大批 `y底=718~720`（贴着画面底边，是镜头前的观众）。

两道过滤（`VideoSource`）：

* **箱体合理性**：太小 / 太扁 / 贴画面底边 → 丢；球员用**独立置信度门槛** 0.40（球仍是 0.25）
* **逐帧人数上限**（`max_players=12` = 两队 10 人 + 裁判），超出按置信度丢
* **投影后用标定覆盖范围过滤**（不能写死 `|y|<=14`：半场标定只覆盖半个球场，
  写死会把"远底线后方的观众"当成场内球员收进来）

效果：逐帧点数从 **19 → 中位 9 / 最大 12**（真实 10 人）。

## 11. 客观校验：`aihoop.cli calcheck`

真视频最大的风险是**标定错了但看起来正常**。所以校验做成可测量的：

```powershell
python -m aihoop.cli calcheck --video data\basketball_game.mp4 --cal data\game_cal.json --out out\calcheck
```

它给三样东西：

| 输出 | 含义 | 判据 |
|---|---|---|
| `camera_motion` | 帧间位移（px/s） | <3 固定机位；>15 单应不可用 |
| `court_fit_score` | 投影线亮脊 / 场内地面亮脊 | ≥1.6 可用；<1.25 不适用 |
| `overlay_*.jpg` | 球场线画到真实帧上 | **给人看**：黄线该压在底线、绿线该压边线 |

自造一张"已知正确"的球场图做对照，该指标能到 **90 倍**；真实广播画面上正确标定约 **1.3~2.3 倍**
（球场线细、被压缩糊过），所以门槛定在 1.6。

### 11.1 球员坐标的两条来源，以及战术层的门槛（真视频必读）

战术层整层都建立在**球员的球场坐标**上，所以坐标从哪来、可不可信，必须先定死。
现在有两条来源，**第二条要额外过一道独立校验**：

| 来源 | 什么时候用 | 是否已校验 | `tactics.json` 字段 |
|---|---|---|---|
| `static_calibration` | 用户标过球场，且通过了自动校验（分辨率/机位匹配 + `court_fit_score` 达标 + 画面里的真篮筐能对上） | ✅ 是 | `position_unverified=false` |
| `sliding_calibration` | 静态标定不可用时**自动逐帧拟合球场线**（`calibcheck.sliding_calibration`），球员坐标由每帧的 H 投影得到 | ⚠️ 部分：质量门槛 + **人工篮筐独立校验** | 过关才出图，且带 `position_unverified=true` + `position_note` |

门槛（写死在 `pipeline._sliding_position_ok`，判据来自滑动标定自己的读数 **加上**
一道独立校验）：

```
① 锚点 anchors >= 2  且  达标率 ok_ratio >= 0.5  且  中位 ratio >= 1.25
② 人工标的篮筐（同一时刻）经这份逐帧标定投影后，必须落在真篮筐 (0, ±1.575) 的 3m 内
   （calibcheck.validate_sliding_with_hoop）
```

**② 这道关不能省 —— 实测这段素材就是被它拦下来的**：

| 读数 | 值 | 说明 |
|---|---|---|
| 滑动标定自报 ratio | **7.17**（锚点中位 2.62、达标率 0.925） | 看着"很好"，其实完全不能证明坐标对 |
| 手标篮筐经它投影（全新起标） | 落在 `(0, ±11.2)`，离真筐 **9.2m** | 坐标整段错了约 9 米 |
| 手标篮筐经它投影（以用户那份退化为起点） | `(-1.5, 8.0)`，离真筐 **6.60m** | 走产品路径时的实测值，同样远超 3m |
| 相邻锚点角点跳变 | 20/200 个锚点跳 120~500px（全是 `kind=full` 重锁） | 说明它在往别的四边形上锁 |

也就是说**线拟合分根本不能证明坐标对**（坏锚点的 ratio 比"看着还行"的锚点还高）。
能用的独立真值只有"与拟合无关的那个点"——人工标的篮筐。
这段素材还试过另外三条真值来源，**都不可用**：篮筐检测器 `runs/detect/rim`
0 帧检出；模板跟踪手标篮筐 5 秒内丢锁；`court_fit_score` 同样会被骗。

> ⚠️ 因此**手工标篮筐时填的那个时刻**（`marks_*.json` 的 `at`）会被一起存下来
> （`hoop.Hoop.t`）——校验必须用**同一时刻**的单应矩阵，拿两个不同时刻的东西
> 对比等于白测。

* 两道都过 → 出战术图，并在 `game.json` / `tactics.json` / 战报第七章 / 战术页
  顶部**四处标注"位置未校验"**（黄色警示条 + ⚠ 免责段落）。
* 任一不过 → **不出**战术图，`game["tactics"]["reason"]` 直接给出读数，例如
  "自动逐帧标定没通过独立校验：人工标的篮筐经这份逐帧标定投到 (0.0, 11.2)，
  离真篮筐 9.20 m"。修法只有一条：**手工重标这个机位**
  （同一帧里点 6 个以上、不在同一条线上的特征点）。

> 为什么要有第二条：真视频里静态标定经常通不过校验（镜头在动，或用户那份标定
> 点位本身就错），而球员坐标其实是有的。老版本只看静态标定的结论就整层跳过，
> 用户看到的是"球员明明检测到了、战术页却一直空着"，**完全不知道为什么**。

**代价写在明处**：逐帧滑动标定约 **3.2 秒/秒视频**（3 分钟素材 ≈10 分钟，
整场 30 分钟不可行）。要更快只能上训练好的球场关键点模型（见 §12 的同款管线）。

### 11.2 保存标定前的两道客观体检（都在 `api._calibration_quality`）

| 体检 | 判据 | 为什么必须做 |
|---|---|---|
| **点位退化** | 点集最大三角形面积占画面 <0.8%、占球场 <0.25%；或最近两点 <2px / 0.25m | 点位几乎共线时，单应矩阵在点位上是**精确解** → **重投影误差必然是 0.00m 左右**。实测一份 4 点标定误差 1.45m、界面显示"可用"，而画面里的篮筐被投到 `(-31.0,-14.0)`、离真篮筐 **33.4m**，热区与战术图整片错位且不报错 |
| **独立校验（真篮筐）** | 用户标过篮筐时，把它用标定投回地面，必须落在真篮筐 `(0, ±1.575)` 的 3m 内 | 只看重投影误差永远发现不了"整份标定位错"。这道校验以前只在"篮下判进球"路径里跑，**有比分牌的转播会整条绕过它** —— 实测 `basketball_match` 那份标定把篮筐投到 **87.3m** 外却照样出图，现在提前到 `VideoSource`，对所有路径生效 |

两道体检**不合格就不写盘**，并把原因（`note` / `degeneracy` / `hoop_check`）
回给界面，标定弹窗直接显示 —— 不再出现"明明标定失败了，界面却说可用"。

**实测（本机）**：`data/uploads/35ea..._852dedd747.mp4`（4 分钟、960×544、
手标过篮筐）：静态标定因点位退化被拒（篮筐偏 33.4m）→ 自动逐帧标定 1201 个锚点、
达标率 0.958 → 产出 `tactics.json` + `tactics_frames.jsonl`（`position_unverified=true`）。

## 12. 球检测重训（把帧级召回从 26% 抬到 48%）

### 12.1 为什么要重训

| 方案 | 每帧候选 | 30 秒总候选 | 结论 |
|---|---|---|---|
| 橙色色块（原方案） | **69.5 个** | 62,587 | 球衣/木地板/皮肤全是橙色，**纯噪声** |
| ShotTracker 现成权重 | 1.08 个 | 971 | 干净了 64 倍，但帧级召回只有 **26%** |
| **重训后** | — | — | 帧级召回 **48.3%** |

### 12.2 完整管线（`scripts/train_ball_detector.py`）

```powershell
python scripts\train_ball_detector.py download
python scripts\train_ball_detector.py convert --classes ball,rim
python scripts\train_ball_detector.py train --epochs 60 --device 0 --workers 0
python scripts\train_ball_detector.py eval --weights runs\detect\ball\weights\best.pt --device 0
```

三个关键设计（少一个都会白训）：

1. **同域数据**：用 `koppolusameer/basketball-coco-player-detection`（NBA 广播画面，
   含 ball/rim/player 标注）。拿野球场的球模型去跑广播远景一样会崩。
2. **尺度匹配**：训练图是 576×576 裁剪块、球中位 17px。
   ultralytics 会把输入缩放到 imgsz，所以要看**缩放后的绝对像素**：
   训练 `imgsz=640`（球≈19px）↔ 推理 `imgsz=1280`（整帧 1.0×，球 8~20px）。**同一量级**。
3. **`eval` 是客观的**：在同一段视频上按帧统计召回，直接和基线比，不靠"感觉变好了"。

### 12.3 接进管线（一行）

```powershell
python -m aihoop.cli video --video data\basketball_game.mp4 --cal data\game_cal.json --out out\mygame
```

代码里只需：

```
VideoSource(..., ball_weights="runs/detect/ball/weights/best.pt")
```

有专用球检测器时，`VideoSource` 会**自动跳过颜色线索**并**旁路轨迹连接** ——
后者是为"颜色噪声时代"设计的关卡，在干净的检测下只会把好数据连成假轨迹
（实测：120 个干净检测点被连成 2 条横跨整段的长轨迹，控球判定因此恒为 0）。

## 13. 传球判据的两条路

| 判据 | 适用 | 原理 |
|---|---|---|
| `possession`（控球人切换） | 球**连续可见**（合成数据、近景固定机位） | 球离谁最近 → 谁控球；换手即传球 |
| `flight`（飞行段反推） | 球**只在空中可见**（广播远景常态） | 飞行段起点最近的人=出球人、终点最近的人=接球人 |

系统会**两条都算、过同一套质量门槛后再比**，平手时优先 `flight`
（它的证据链更直接：球真的从 A 飞到了 B）。

### 13.1 必须有的清洗（`tactics.clean_passes()`）

真视频实测到的两类噪声，不清洗会污染结论：

* **位移过小的假传球**（球在球员身边抖一下就算换手）→ 过滤 `dist < 2m`
* **同一次传球被算两次**（A→B 后紧接着 B→A，球检测在两人之间跳）→ 2.5s 内同向/反向重复直接去重

效果（15 秒广播片段）：

```
清洗前：控球路径 5 次（含 1 条 0.6m 假传球 + 1 条重复计数）
清洗后：3 条事件 —— 1 次抢断（3.7m）+ 2 次传球（9.7m / 6.2m）
```

**宁可少而准**：答辩时一次错传球被追问，比少两次传球难看得多。

## 14. 实测天花板（**诚实清单，答辩可以照讲**）

| 限制 | 实测值 | 能修吗 |
|---|---|---|
| 球被遮挡就丢 | 帧级召回 48.3%（遮挡期间无检测） | 补标注重训可再抬，但消不掉 |
| 球员外观不可分 | BoT-SORT **开 ReID 反而更差**（41→47 条轨迹） | 广播远景球员仅 40~70px，外观特征本身不可分 |
| 球员 ID 碎片 | 15 秒 41 条轨迹（真实 10 人） | 需球衣号 OCR；**不影响俯视战术图的位置** |
| 球衣颜色分队 | 从退化的 55:1 修到 19:37（分离度 3.68） | 用 `jersey_teams` 参数人工指定最稳 |
| 移动镜头 | 逐帧滑动标定 98% 达标 | 但成本 ≈3.2 秒/秒视频，长视频不可行 |
| 单目球高度 | 球在空中时地面投影有几米偏差 | 物理限制，双机位才能解 |

**关键区分**（这条答辩很容易被问）：

| 受 ID 碎片影响 ❌ | 不受影响 ✅ |
|---|---|
| 传球网络里"谁传给谁"的标签 | **俯视战术图的位置**（逐帧点位正确） |
| 球员个人统计的连续性 | **阵型识别、空间指标**（只用位置，不用身份） |

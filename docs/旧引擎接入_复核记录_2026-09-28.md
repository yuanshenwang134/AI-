### 2.4 与旧项目自己的记录对照（重要）

这两段失败**不是移植引入的**，旧项目 2026-09-17 就诊断过，而且写下了根因与"下一步"：

- `D:\dsh_folder\hoopai_投篮检测_旧版\docs\diagnose_unseen_make.md`
  - §1：day_outdoor 那记 25.2s 出手、25.53s 入筐的**命中**被软件判成 `miss`；
    原因不是球没找到，而是"命中"要求一串**真实观测**向下跨过筐心高度（`crossing_t` 非空），
    而这一球在筐附近被筐沿/网/人挡了 5 帧，`crossing_t` 永远拿不到 → 超时判 `miss`。
  - §5 原文结论：**"此时的结果不该是'未中'（`miss` 表示'我们确认它没进'），而更接近'结果未知'。"**
  - §3：夜间那段是**筐被锁在完全错误的对象上**（`(87.5,59.4)` 顶了 1.2 秒以上，真筐在 `(364,330)`，
    跳变 ~390px），出手根本没建立起来 → 0 事件；另有 0.5 秒完全没有球检测。
- `D:\dsh_folder\hoopai_投篮检测_旧版\docs\strict_shot_gate.md`
  - "真正的机制：软件把两个篮筐来回当成同一个"——转播画面里前后场两个筐被当成一个，
    由此**传球被记成出手**、"划框而过被判进球"。这正是用户当初提的那两条意见的根因。
  - 缓解办法写的是既有功能：**把筐钉死**（`hoop_roi` + `hoop_roi_mode: force`）；
    代码层面的"筐身份稳定性"被列进下一步，**并明确写着"本次没有做"**。

也就是说：移植版继承的是**旧项目已知未解决**的两个缺口，而不是引入新 bug。
按我方的证据分级，这两段属于 **"已知边界，不能算准确率"**。

## 三、本轮新发现的问题（按严重度）

### P1-a 复核片段"修复"是死字段（声明与实际不符）

- 写入侧确实做了：`adapter.py:31` 把 `clip_end` 记成**判定时刻 + 1.5s**
  （注释也写明"不能只截离手后 1.5s"），`rules.py:370` 把它取 `max` 后存进 `Shot.clip_end`；
  单测 `tests/test_shot_legacy_engine.py:126` 也在断言它。
- **但全仓没有任何消费者**：
  - `pipeline.py:663-674 _shot_event()` 序列化时**没有** `clip_start/clip_end` 两个键
    → `game.json` 的 timeline 行里根本没有它们（实测打印过键列表），前端拿不到；
  - `highlight.py:88-89` 自己算 `start = s.t - clip_pad_before` / `end = s.t + clip_pad_after`，
    **不读** `s.clip_start/clip_end` → 高光/片段仍可能在球飞到筐之前就切掉；
  - `web/**/*.js` 全仓没有一处读 `clip_start/clip_end`（只有 `web/_gen_demo.js` 在写假数据）；
  - 复盘页没有"片段"概念，是 **seek 到某个时刻后自由播放**：`overview.js:300-302`
    `seek = max(0, (crossing_t ?? t) - (crossing ? 1 : 0.6))`；`overview.js:366`
    只有在 `crossing_t != null` 时才给出「看篮下 hh:mm」按钮。

  后果：旧引擎在**遮挡入筐**时 `crossing_t=None`（旧项目 §1 的诊断），这时既没有「看篮下」按钮，
  跳转点又只是出手前 0.6s —— 用户"看不到最终落筐画面"的体感**没有被修掉**。

### P1-b 只标中心时，篮筐身份没有任何约束（旧项目 §"两个筐互跳"的坑默认开着）

- `stream.py:78-80`：`hint`（人工标点的中心）**只在筐跟踪器还没初始化时**用来挑最近的候选；
  注释也写明了"不把无尺寸的点变成静态篮筐"。初始化之后完全交给旧跟踪器。
- `stream.py:82-84`：只有**同时给了半径**（`manual_hoop.rx>0 and ry>0`）才会每帧硬覆盖筐。
- `scorer.py:207`：`rim_identity_lock` 默认 **False**；移植的 `stream.py:14-22` 配置里**没有这个键**
  （旧 `config.yaml` 里也没有，是老项目列为 P1 但没实现的那条）。
- 跳变上限是 `max(60.0, 3.0 * rim.w)`，远距重捕只需连续 6 帧 → 一步就能跳到另一个筐上
  （旧 `config.yaml`：`rim_readopt_far_frames: 6`；移植一致）。

用户现在的标注方式恰好是**只点中心**（我在上一轮把界面改成中心为主）。
在这条路径上，"传球被记成出手""划框而过判进球"这两个老问题**没有防护**。

### P2-a 同一球两次运行的时间码会差 1 秒以上（出手归属不稳）

同一个 nathan 球：关球员跟踪时 `t=1.74/6.34/...`，开球员跟踪时 `t=1.13/5.77/...`；
day_outdoor 更明显：`11.61 → 10.84`、`25.83 → 24.49`（Δ 最大 **1.34s**）。
原因是 `release_t` 的来源不同（球本身 vs 球员脚下 `release_source`），
而拥挤场景里球员跟踪假阳性很多（day_outdoor `player_track.players=24`），
出手被绑到 `T85/T197/T277/UNASSIGNED` 等不同 id 上。
后果：用户对比两次运行会以为"结果变了"；复核片段的时间窗也跟着漂。

### P2-b 无球场标定时，出手位置是占位符、分值恒为 2

`adapter.py:23-26`：`x=0., y=-1.575`（占位）、`location_source='rim_placeholder'`、
`forced_value=2` + `value_assumed=True`；只有"有标定 + `release_source=='player_feet'`"
才会换成真实场地坐标（`adapter.py:34-39`）。
nathan 那天两跑都带 `location_unknown` + `value_assumed` 标签。
后果：热区图/出手距离/2 分还是 3 分在未标定素材上**全是假的**，界面必须说清楚，
否则又是"看起来有热图、其实全错"。

### P3-a 评测脚本的表格不能用来讲计分链路

`scripts/eval_timed_truth.py:58` 固定 `detect_players=False` → `team` 必然未知 →
`adapter.py:22/27` 给每条投篮加 `team_unknown` + `needs_review`、`counts_for_score=False`。
所以"全部 `needs_review`""得分 0:0"是**评测路径的产物**，不是产品行为
（2.1 的产品路径没有这些标签，得分 10:0）。
另外 `strict_shot_gate` 两种模式（rim 权重 / 无权重）输出**逐字节相同**，那个开关目前是空转的。

### P3-b `legacy_shots/` 改动不会触发热重载

`scripts/serve_reload.py:39` 只 `glob("*.py")` 监听 `src/aihoop/` 这一层，
不递归子目录 → 改 `src/aihoop/legacy_shots/*.py` 后**必须手动重启后端**，
否则跑的仍是老模块。本轮就踩到过（后端 `code_loaded_at 09:55:08`）。

### P3-c 类内回退默认与产品配置不一致（将来的坑）

`scorer.py:211` 类内默认 `miss_timeout_s=2.5`、`scorer.py:223` `rim_readopt_far_frames=2`，
而产品配置传的是 **3.5 / 6**（与旧 `config.yaml` 一致）。
任何人直接 `ScoreEngine({})` 就会静默换成另一套阈值。

## 五、给队友的最小改动清单（建议顺序）

1. **把复核片段真正接上**（二选一，别只改数据）：
   - 在 `pipeline.py:_shot_event()` 里补 `"clip_start"/"clip_end"`，复盘页按
     `[clip_start, clip_end]` 播放并把区间画在进度条上；或者
   - 在 `highlight.py:88-89` 改成优先读 `s.clip_start/s.clip_end`（有值就用）。
   另外：`crossing_t=None` 的旧引擎事件，至少给一个"判定收尾"跳转（旧事件的
   `t` 就是判定时刻，可以直接用），否则遮挡入筐的球永远没有"看篮下"入口。
2. **只标中心时给筐加约束**：把提示的中心 + 首次确认时的筐宽记下来，
   之后候选超出该宽度 N 倍就不采纳；或产品侧在"只标中心"时默认打开
   `rim_identity_lock`（`scorer.py:207`）。**别直接改默认**——先在
   dairy / nathan / fixedcam 三段上跑回归（旧项目的教训：改默认必须整段回归）。
3. **遮挡入筐要记"未知"而不是"未中"**：旧引擎自己写过结论
   （`docs/diagnose_unseen_make.md` §5）。移植版 `scorer.py:454-459` 的分支仍然是
   "只要 `at.entered` 为真就记 `miss`"，只在 `not entered` 且球也不新鲜时才记 `uncertain`
   —— 也就是说"球确实进过筐口一带、但拿不到向下穿越证据"这一档仍然输出 `miss`
   （本机 day_outdoor 真值#3 就是这样被判成 `missed`）。建议把它判 `uncertain`
   （对应我方几何路径这一轮加的 `cross_rim_contact`/未知）。
   两套引擎对同一球给出不同结论时，用户只会认为"系统坏了"。
4. 统一 `scorer.py` 类内回退默认（3.5 / 6），别和产品配置差两套值。
5. 讲计分链路时用 `scripts/probe_product_scoring.py`（产品路径），
   不要用 `detect_players=False` 的评测表。

**可以对外说的**：默认引擎已切到旧引擎、命中/未中/未知都进列表、建议不计分、
逐帧依据与模型指纹齐全、nathan 产品路径 6 次出手与真值序列一致且得分 10:0。
**还不能说的**："复核片段已修好"、"没漏球"、"标了中心就不会认错两个筐"，
以及任何跨场景准确率（day/night 两段是旧项目自己标注的未训练场景，
另有 dairy/fixedcam/nathan 进过旧 v6 训练集，存在过拟合风险）。

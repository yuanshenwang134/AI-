### 3.1 归因修正：4→2 必须用"同参数配对"来比

### 3.3 新发现：不是"跳"，是**逐帧走位**（跳变闸门拦不住）

> **⚠ 这一节的推论同样已被推翻**：走位是跟着**真实篮筐与镜头一起动**的，属正常行为，
> **不能据此收紧跳变限制**。详见 `docs\篮筐跟踪缺陷诊断_切分与结果关联_2026-09-29.md`。
> 走位轨迹本身（数值）仍然有效，可作为参考。

复核方要求看画面，我先把逐帧依据里的跟踪位置拉成时间线，发现一个比"远处重捕"更根本的机制：

```
段1（真筐）：t=2.27 初始化 cx=635 → 2.64 cx=689 → 4.50 cx=662
            然后 0.9 秒内平滑滑走：4.57 cx=635 → 5.37 cx=131   （530px，全程状态=tracked）
段2：t=8.24 reacquired_far 跳到 cx=1841
            随后 4.5 秒平滑滑回：9.31 cx=1433 → 9.81 cx=1241 → 10.31 cx=1117
            → 10.81 cx=1087 → 11.31 cx=1076 → 12.81 cx=1049
      之后停在 cx≈1042~1049（右筐簇）直到 17.8s 以后
```

关键点：**每一步几十像素，全都小于跳变上限（`max(60, 3×筐宽)`≈354px）**，
所以 `jump_rejected` 一次都不会触发 —— 跟踪框可以"走"到完全不同的物体上，
而现有闸门只看单帧跳变。这也解释了为什么旧项目记录里
day_outdoor 会逐帧"走" `(155)→(203)→(231)→(248)→(259)→(266)→(271)`。

**对被过滤那两条事件的直接影响**：13.51 / 17.08 秒判罚时用的筐位是
**(1048,238) / (1043,239)**，也就是**右侧框簇**（另一个筐的位置），
而这条证据链的起点是 8.24 秒那次假锁（1841）。
所以"这两条该不该删"要连着**走位过程**一起看，不能只看判罚帧。

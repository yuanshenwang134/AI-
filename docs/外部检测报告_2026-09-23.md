## 2. 缺陷清单

### P0-1 比分牌自动定位选中了没有文字的区域 → OCR 命中 0

**现象**：`POST /api/scoreboard/ocr` 只给 `video_path`（自动定位）时，返回 `ocr_hit = 0/480`、`final = None:None`。

**证据**：
```
method = "auto_static_overlay"     box = [1092, 279, 314, 30]
读到 0/480 张，得分事件 0 条，最终比分 None:None
分析任务里同样如此：meta.scoreboard = {"source":"template","frames_read":2398,"frames_hit":0,
                                     "bug":{"x":1092,"y":279,"w":314,"h":30}}
```
把整帧切成 6×3 网格逐块 OCR 之后，真正的比分条位置是（全画面唯一含比分文本的区域）：
```
t=1.0s   x 640~1280, y 0~180  →  "FHS AHS 31 3 rd Qtr"（该帧 OCR 漏读了 FHS 的分数）
t=238.0s x 640~1280, y 0~180  →  "FHS 38 AHS 38 3 rd Qtr"
→ 实测可用框（像素）：x0=600, y0=100, x1=1360, y1=180（归一化 [0.3125,0.0926,0.7083,0.1667]）
```
自动定位给出的 `y=279` 与真实比分条（`y≈100~180`）**完全不重叠**；该区域 OCR 三次全空。

**根因定位**：`src/aihoop/api.py:1440-1446` 走 `locate_score_bug_static()`，
其判据写在 `src/aihoop/scoreboard.py:488-491`：**「按叠加层不随时间变化定位」**。
但**比分数字本来就会随时间变化**（31 → 38），"不变化"这条判据与"找比分数字"相互矛盾：
它更可能选中静态水印/台标底色，而不是会跳数字的区域。

**建议修法**（任一，建议 1+3 组合）：
1. 定位阶段**不要要求整块不变**，改为：对候选叠加层区域跑一次"时间差分 + 数字存在性"，找**既稳定出现、又包含随时间变化的数字**的区域；
2. 用 OCR 结果反选：对 top-N 候选区域各抽 5~10 帧做 OCR，选**能解析出分数模式**（`队名 1~3 位数字 … 队名 1~3 位数字`，或含 `:`）的区域——判据从"图像不变"换成"语义像比分"；
3. 保留并优先使用"手动框选"路径（实测有效），当自动定位结果 OCR 命中率过低时**自动回退到提示用户框选**，而不是静默返回 0 命中。

**验收**：`POST /api/scoreboard/ocr`（只给 `video_path`，不给 `box`/`start`）在 game_04 上
必须满足 `ocr_hit >= 0.9 * n_crops`、`final == {"home":38,"away":38}`、`n_events == 10`。

### P0-2 比分基线缺失 → 真实读数被当成误读全部丢弃

**现象**：即使框对了，不给 `start` 时结果是 `final 3:3` + 2 条假事件。

**证据**：
```
start=None            → ocr_hit=480/480, final={'home':3,'away':3}, n_events=2, rejected=929
                        events: {"t":0.0,"team":"away","delta":3,"value":3}
                                {"t":75.58,"team":"home","delta":3,"value":3}
start={'home':31,'away':31} → final={'home':38,'away':38}, n_events=10, rejected=271
                        home +2+2+2+1 = +7，away +2+1+1+1+1+1 = +7   ← 与真值一致
```

**根因定位**：`scripts/read_marked_scoreboard.py:127` `cur = int(start.get(team, 0))`
——基线默认 **0**；而 `:133` 的过滤是 `if v - cur > max_delta(3): 丢弃`。
于是第一个真实读数 **31** 被判成"一次跳变超过 3 分（多半是误读）"**丢弃**，
整条序列再也无法建立基线，最终只剩偶然读到的小数字，`final` 变成 3:3。
（`rejected` 从 929 降到 271，也说明大量真实读数原先被这条过滤吃掉。）

**建议修法**：
- `start` 缺失时，**用第一次通过格式校验的读数作为带入基线**（并在产物里标注 `baseline_from="video"`），
  `max_delta` 只在其后生效；
- 或把"首次读到 = 建立基线"与"后续读数 = 计分增量"显式分成两个阶段（现在混在一起）；
- `start` 若给了但与首帧读数差很多（如 >20 分），给出告警而不是静默采用。

**验收**：不给 `start`，仅凭 OCR 自动读数，`final` 仍应为 `38:38`、`n_events == 10`。

### P0-3 按阅读顺序取前两个数字 → 节次数字污染比分

**现象**：出现 `t=0.0 team=away delta=3` 这种"开场就加 3 分"的假事件。

**证据**：`t=1.0s` 那帧 OCR 只读出 `"FHS AHS 31 3 rd Qtr"`（FHS 的分数漏读），
按阅读顺序取 `\d{1,3}` 得到 `[31, 3]` → 主队 31、**客队 3（把 "3 rd Qtr" 的 3 当成了客队比分）**。

**根因定位**：`scripts/read_marked_scoreboard.py:105-114`
```python
nums = [int(m.group(0)) for m in re.finditer(r"\d{1,3}", txt or "")]
if len(nums) >= 2:
    per.setdefault("home", []).append((it["t"], nums[0]))
    per.setdefault("away", []).append((it["t"], nums[1]))
```
—— 纯位置假设（左=主队、右=客队），既不认队名，也不排除节次/时间区域。

**建议修法**：
1. 按**队名标签**取数：在文本里找配置的队名（本素材为 `FHS`/`AHS`），取每个队名**之后**第一个 1~3 位数字；
2. 从裁剪区域里**排除节次/计时区**（或在 OCR 前把该区域涂黑），避免 `3 rd Qtr` 类文本进入数字池；
3. 定位不到队名时，退化为当前位置假设，但**必须记录 `parse_mode`**，并且该读数降权；
4. 校验：单帧内两个数字应满足"与上一帧差值 ≤3"的**双队联合约束**，不满足则整帧丢弃（而不是各队独立丢弃）。

**验收**：构造三条输入文本做单元测试（见第 3 节），`build_events` 的 `final` 均应为 `{"home":38,"away":38}` 或按给定 `start` 递增，且**不得出现 delta 来自节次数字的事件**。

### P0-4 `players.json` 的队别与 `events.jsonl` / `game.json` 相反

**现象**：同一份产物里，逐球员数据与事件/球队汇总互相矛盾。

**证据**（`out/game04_rerun_20260923_000735`）：

| player_id | `events.jsonl` 的 team | `players.json` / `stats.csv` 的 team |
|---|---|---|
| T7861 | home（179.41s 命中） | home ✓ |
| T9478 | **away**（200.93s 未中） | **home** ✗ |
| T9499 | **home**（206.21s 命中） | **away** ✗ |

球队汇总按事件算：`home 4 : away 0`；按 `stats.csv` 的球员行相加却是 `home 2 : away 2`。
另外 `game.json.teams[*].name` 直接取了球员名：`"球员860"` / `"球员1017"`（应为队名）。

**根因定位**：队别存在**两条完全不同的逻辑**，各自算各自的，谁也不引用谁：

| 用途 | 位置 | 逻辑 |
|---|---|---|
| **事件侧**（`events.jsonl` / `game.json`） | `src/aihoop/sources.py:1921 _visual_attempts()`：`:2042 team_of = {}`、`:2049 team_of[top[0]], team_of[top[1]] = "home","away"`、`:2068 team = team_of.get(pid)` | **启发式**：把"出手次数最多的两名球员"直接当成主队/客队；再认不出的球员按"出手点横向位置 < 筐 x 中位 → home，否则 away"兜底 |
| **球员侧**（`players.json` / `stats.csv`） | `src/aihoop/sources.py:2561 _assign_teams()` → `:2612 two_means()` → `:2676 rt.players[pid].team = "home" if is_home else "away"` | **球衣颜色 2 聚类**（色相/饱和度/明度里选自分离度最高的那个特征） |

两套逻辑在"只有 3 次出手"的片段上几乎必然矛盾：事件侧的 `top` 只有两个人、第三个人落到位置兜底，
而球员侧完全按球衣颜色分。此外事件侧还会把 `rt.players[pid].name` 覆写成 `球员N`（`:2062-2070`），
所以 `game.json.teams[*].name` 变成 `"球员860"` 这种由跟踪 ID 派生的名字。

**建议修法**：
1. **单一数据源**：队别只算一次（建议以球衣配色为主、人工指认为准），写入一张 `pid -> team` 映射，
   事件、球员统计、球队汇总、队名全部从这张表取；`_visual_attempts` 里的 `team_of` 启发式删除或仅作最后兜底并标注 `team_source="heuristic"`；
2. 若保留两套，产物必须带 `team_source` 字段并在不一致时报错，而不是静默产出互相矛盾的数据；
3. 产物自检：`sum(players.points by team) == teams[*].stats.points` 必须成立，否则**任务标为 error**；
4. 队名不要用球员名兜底，缺失时写 `"主队"/"客队"` 或留空并标注 `team_name_unknown`。

**验收**：game_04 重跑后，`players.json` 中 T9499 的 team 必须与 `events.jsonl` 中 206.21s 那条一致；
且逐球员 points 按队求和等于 `game.json.teams[*].stats.points`。

### P1-5 视频任务硬性要求"先标定球场"，把"只读比分"这条路也堵死

**现象**：请求里已经 `detect_players=false` + `score_policy="scoreboard"`（只想要比分与得分事件），
仍然 `RuntimeError: 尚未标定球场`，任务 1 秒失败、`out_dir` 为空。

**证据**：
```
POST /api/jobs {"source":"video","video_path":"...game_04...","scoreboard_events":"data/sb_events_game_04_....json",
                "score_policy":"scoreboard","detect_players":false,"auto_sliding":false}
→ job 551dee0c76c3  status=error  progress=0.02
  error: RuntimeError: 尚未标定球场。在界面上点「标球场」…
```
字段注释里写的是：`detect_players=False`（"只要比分 + 每次得分事件时把它关掉，3 分钟视频从几十分钟降到一两分钟"）
——**这个被推荐的用法在当前代码里无法使用**。

**根因定位**：`src/aihoop/api.py:258-269`，`source == "video"` 分支**无条件**要求
`_find_calibration_for(video)` 或 `DATA/calibration.json` 存在，既不检查 `detect_players`，也不检查 `score_policy`。

**建议修法**：把标定要求与"是否需要球场坐标的下游"绑定：
- `detect_players=false` 且 `score_policy="scoreboard"`（或 `--fast`）时，允许 `cal=None`，
  产物里显式写 `calibration_valid=false`、`court_outputs_available=false`，位置类结论全部标注为不可用；
- 其余情况保持现在的硬性要求（这条要求本身是对的，问题只在于没有例外路径）。

**验收**：上述请求在无任何标定文件时也能跑完，产物 `game.json.score` 等于比分牌读数带入的结果，
且 `calibration_valid=false`、不输出任何米制位置结论。

### P1-6 `scoreboard_events` / `score_policy` 在 `jsonl` 分支被忽略

**现象**：用 `source="jsonl"`（不需要标定）+ 显式传 `scoreboard_events` + `score_policy="scoreboard"`，

### P2-7 `probe_footage.py` 的素材门槛与 `check_video_fit.py` 的结论互相矛盾

**现象**：同一段素材，两个自带工具给出相反结论。

| 工具 | 判据 | 结论 |
|---|---|---|
| `scripts/probe_footage.py`（`"像球"圆块`启发式） | 球径 ≥ 30px、**球径/画面宽 ≥ 1/30**、筐宽 ≥ 300px（见该文件第 7-10 行） | ❌ 不够用 |
| `scripts/check_video_fit.py`（用训练好的检测器） | 球检测命中率 > 40%、机位固定 < 3px/s、球员框 > 100px | ✅ 适合（**球命中 80%**） |

**证据**：
- 960×540 广角素材：`probe_footage` 给出球径中位 **3.5 px**、球径/画面宽 **1/274** → 判"不够用"；
  而同一素材上检测器球命中率 **80%**、旧管线编号 7 次出手全部检出。
- game_04（1920×1080 转播）：本机用自训练权重实测**有球帧 65.3%**，球宽中位 **52.8 px**，
  但 `1/30` 门槛等价于要求 **64 px** → **仍会被拒**，尽管检测器可用。

**根因**：门槛是按"近距离仰拍"定的（球大），对广角/转播素材系统性偏严；
而实际决定成败的是**检测器召回**，不是色块球径。

**建议修法**：
1. 把"素材是否可用"的主判据换成**在若干抽样帧上跑一次真实检测器**的召回率（`check_video_fit` 那条路），
   色块球径降级为"辅助提示"；
2. 若保留 `1/30`，必须说明它是**针对手机近距离仰拍**的门槛，并在文案里给出"检测器可用但色块不可用"的第二种结论，
   不要让上传页把这类素材直接判死；
3. 两个工具的结论应当一致（同一份"素材体检"结论被上传页与报告共用）。

**验收**：对同一段素材，两个工具结论一致；game_04 与 960×540 广角素材都应给出"可自动识别（依据：检测器召回）"。

### P3-8 `PYTHONPATH` 被覆盖（自检假失败 / 服务起不来）

**现象**：在依赖装在自定义目录的机器上直接跑：
- `python scripts/check_all.py` → 4 项 FAIL，报 `ModuleNotFoundError: No module named 'fastapi'`（**假失败**）；
- `启动后端.bat` / `python scripts/serve_reload.py 8000` → 子进程 `ModuleNotFoundError: No module named 'uvicorn'`。

**根因定位**：
- `scripts/check_all.py:29` `ENV = {"PYTHONPATH": str(ROOT / "src"), ...}`
- `scripts/serve_reload.py:97` `env["PYTHONPATH"] = str(SRC)`

两处都是**覆盖**，而不是**追加**；子进程因此丢失依赖目录（`aihoop` 能找到是因为 `src` 还在）。

**建议修法**：
```python
env["PYTHONPATH"] = os.pathsep.join(
    [str(SRC)] + [p for p in (os.environ.get("PYTHONPATH") or "").split(os.pathsep) if p])
```
（`check_all.py` 同理。）这样 pip 全局安装的机器行为不变，自定义依赖目录的机器也能跑通。

**验收**：`PYTHONPATH` 指向自定义依赖目录时，`check_all.py` 11 组全绿、`serve_reload.py` 能起服务。

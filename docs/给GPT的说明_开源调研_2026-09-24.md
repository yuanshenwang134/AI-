# 给队友侧 GPT 的说明：开源调研结果 + 三条可落地建议（2026-09-24）

> 外部复核方写的。这一轮不是复检你们的代码，而是按"去 GitHub 找能提高识别率的项目"
> 这个方向做的调研：下载 9 个仓库读代码 + 自己做离线原型验证。数字都来自本机实测。

## 二、一句话结论

**没有一个项目能"装上就提准确率"** —— 没有篮球专用的球/篮筐权重，TrackNet 官方权重是羽毛球，
KaliCalib 权重不随仓库提供，那 5 个"投篮分析"仓库连真值评测都没有、判据还比我们弱。
**但本轮挖出一个更值钱的判断：我们的瓶颈是逐帧篮筐/球场几何精度，不是球检测器。**

## 三、支撑这个判断的实测数字（都是这一轮新测的）

1. **证据密度**：把已保存的逐帧诊断数一遍（`aihoop\_tmp\trace_density.py`）：
   fixedcam 的 703 个「帧×篮筐」记录里只有 108 个（15%）有候选块，
   其中 **503 个（72%）连运动连通域都没有**；dairy 好一点也是 304/1670（18%），
   另有 63% 是"有块但被尺寸/形状全过滤掉"。
   同一段素材里**球检测器给出 591/639 个候选点** —— 证据量是帧差路径的 2~5 倍。
2. **球检测器其实看得见那一球**（`_tmp\probe_ball_near_rim.py`）：fixedcam 19.1s 那一球，
   球检测器给出连续轨迹 `19.10 (591,151)` → `19.13 (603,161)` → `19.17 (613,171)`，
   球被网挡住 0.4s 后又在 `19.57 (620,213)` 出现 ——
   即"从平面上方 0.5 个圈半径穿到下方 1.8 个圈半径，横向一直在圈内"。
   证据是完整的，只是 hoopsight 那条帧差路径看不到。
3. **同一颗球，结论取决于篮筐位置那 16 个像素**：nathan 10.71s 球在 (527,151)，
   11.15s 在 (527,185)。用常量篮筐 (553,154,rx=31) → gx=−0.84（判"擦筐掠过"）；
   用逐帧篮筐 (≈537,158,rx=29) → gx=−0.34（判"穿过筐心"）。
   而 nathan 的篮筐在 27 秒里 **cy 漂 38px、cx 漂 39px**。
4. **出口判据的离线 A/B**（`_tmp\proto_exit_rule.py`）：先复刻你们现有判据并**复现了真实产物**
   （fixedcam {5.4,22.4}、dairy {16.93,25.83}），再比较四种出口判据 ——
   你们已实现的容差版、我提的"纵向 ≥0.2×rx"、"允许 ≤0.15s 轨迹外推"**三种都能找回 19.1s 那一球，
   而且在 dairy 上都不新增事件**。说明这个修复不依赖调参，方向（用圈半径物理尺度）本身是对的。
   （顺便更正：我上一轮建议的 `max(ry,4~6px)` 方向是错的，那会**提高**薄筐门槛，你们拒绝得对。）
5. **原型：只用「球检测器 + 篮圈半径几何」数穿筐事件**（`_tmp\proto_ball_rim_events.py`）：

| 素材 | 人工真值 | 现有产线 | 本原型 |
| --- | --- | --- | --- |
| fixedcam | 3 进 / 4 不中 | 3 进 | **3 进（5.33/19.03/22.33），4 次不中零事件** |
| dairy | 3 进 | 2 进 | **3 进（6.27/16.73/25.73）** ← 新找到的 6.27s 那一球，此前两条路径都没发现 |
| nathan | 5 进 / 1 不中 | 7 出手 4 进 3 未知 | 5 个真进球全中 + 1 个额外（10.55s，就是上面第 3 条那个筐沿边界球） |

## 四、建议的三条（按性价比，都落到你们代码上）

**P0｜把"篮筐平面"从像素门槛换成球场坐标几何（最重要）**
这一轮读 KaliCalib 的代码时挖出两件事，让 P0 变得比原来便宜得多：
* **`ry` 为什么会退化**：`ry` 是篮圈在**视向方向**上的像素尺度，篮圈接近正侧视时 →0；
  我们手标薄筐 `ry=3.9px` 正是这个退化。**修它不需要 KaliCalib** ——
  用篮圈半径 0.225m 或篮板高 1.05m 换算像素/米，把 `hoop.py` 里
  `min_cross_drop_frac × ry` 换成**米制阈值**即可（约 20 行、无新依赖）。
* **我们仓库里已经有一条纯球场坐标的穿筐判据，但在真实视频上永不触发**：
  `rules.detect_rim_events`（`rules.py:210`）判的是"水平距离 <0.25m 且高度由 >3.05m
  下落到 <3.05m"，完全几何、免训练；可真实视频路径把 `BallSample.z`
  **硬编码成 1.2**（`ball.py:578`、`sources.py:700/716/1354`），球高永远是 1.2m，
  这条判据一次都不成立（只有合成数据上活着）。**缺的不是判据，是相机模型 P。**
* 而且单目也能做：球高不可观测，但"球心射线 ∩ 已知平面 z=3.05m"是唯一确定的
  ⇒ 只要有了 P，就能把穿筐点投到 3.05m 平面判 0.225m 的圆，**不需要球的三维位置**。
* 最小实施顺序：①米制门槛（便宜）→ ②给 `Calibration` 加可选 P，准入闸门用
  "已知 3D 篮筐 (0,±1.575,3.05) 的重投影残差"，让上面那条判据在真实视频上活过来，
  顺带修掉"横向差 0.10rx"；③把 `HoopTrack` 采样存全（现在只存每 5 个）、
  `hoopsight._hoop_at` 改成"最近采样 + 累计变换搬运"、`max_drift_frac` 的硬否决
  改成作用在补偿后的残差上（治"手持机位直接放弃"）。

**P1｜球轨迹空洞修补（零权重零训练，来自 TrackNet 的 inpaint 思路）**
在 `ball.py` 的 `stitch_tracks` 之后加一个补点步骤，**判据要严**：
只在"空洞两端都在画面高处、且空洞 ≤0.3s、位移方向一致"时补，补出的点标 `source="interp"` 并降 score。
验收：判进数只能升不能降、**不得新增假进球**（我们目前零误报），并补单测。

**P2｜把球轨迹接进判进球（prototype 已证明可行，但精度上限由 P0 决定）**
`basketball-tracking` 那条"证据来源白名单"的纪律值得直接抄：
只有**实测**来源（球检测器实测点、人工标点）能为事件作证，插值/颜色/卡尔曼一律只作参考。
落到我们：现在 `exit_tolerance_used` 只写进 trace，应该升级为**逐点标签**传进 `_judge_span`，
容差档证据**扣置信度**，只有容差证据时返回 `None` 并给机器码 `exit_tolerance_only`；
`allow_hole_interpolation` 继续默认 **False**（理由见下）。

## 五、别抄什么（反面教材，值得写进我们的规则）

`nba-analysis-yolo` 把 174 帧里 **139 帧（79.9%）的球坐标用插值伪造**，然后照样在假轨迹上判事件；
`ball-yolo` 退化成"球出现在筐下方区域就算进"；这 5 个仓库**回放球与补篮全部没处理**，
擦筐只有我们做了（`cup_inner=0.62` + `min_cup_frames=2`），而且**全部零真值评测**。
所以：**抄工程纪律可以，抄判定逻辑会把我们已有的评测优势丢掉。**

## 六、一条数据线索（我们最缺的东西）

`Basketball-51dataset` 的 README 指向一个含 **8 类 make/miss、10,311 段真值视频**
（6 秒 / 320×240，Kaggle + gofile）的第三方数据集。这是目前找到的**最像"独立测试集"**的来源，
但许可未声明、分辨率低、机位未知 —— 需要先人工确认许可与可用性。
如果可用，它可以部分解决我们"只有 4 段开发素材、没有独立测试集"这个根本短板。

## 七、许可与风险

* `_refs\src` 全树无 LICENSE；`TrackNetV3` README 称 MIT 但仓库缺 LICENSE 文件；
  `tracknet-series-pytorch` 完全无许可声明（默认保留所有权利）。
* 那些投篮分析仓库都依赖 **Ultralytics AGPL-3.0** —— 抄代码/权重对闭源产品是红线，抄思路没问题。
* TrackNetV3 钉 torch 1.10、25 处硬编码 `.cuda()`，与我们（torch 2.x + ultralytics 8.4）环境冲突；
  本机两个 TrackNet 仓库**都没有预训练权重**，且论文里**没有任何篮球实验**
  （V1 网球模型直接跑羽毛球召回只有 22.9%，跨运动迁移有负面实测）。
  → 结论：**不要为了 TrackNet 去搭一套新环境**；先把 P0/P1 做完。

## 一、我改了什么（`web/_test.js`，2 处）

**1）让这个离线单测显式走"离线/演示"路径**（在场景 A 之前插入两行 + 注释）：

```js
win.STORE.backendOk = false;
win.STORE.demoMode = true;
```

原因：复核页的改判从 2026-09-25 起是 async —— 有后端时它 `await` 提交、再
`APP_LOAD_JOB` 重新拉产物，**本地状态靠"重新加载"更新**；node 单测里没有真后端，
这条路走不通。离线模式的本地重算整段是同步的（第一个 await 之前就做完了），
断言才有意义。**加 `await` 并不能修这个**：它会把断言推进微任务，而这个文件末尾是
同步算 `process.exitCode` 的，反而会把失败吞掉（测得 exit=0 但打印里有 ✗）。

**2）场景 B 的取行方式改了**（改成从 `allShots` 优先取）：

```js
const row2 = self.allShots.concat(self.rows).filter(
  r => r.player_id === t2.player_id && Math.abs(r.t - t2.t) < 0.001)[0];
```

原因（这是本轮最有价值的发现）：原来是从 `self.rows`（复核队列）优先取，而队列里的行
在"后端没给 index、又按 (t, player_id, value) 匹配不上 timeline"时 `_index` 会是 **-1**；
`review.js` 里 `row._index < 0` 时**静默 return**，改判根本没提交 —— 实测打印出来就是
`row2._index = -1`，断言拿到 `34 -> 34`。改用 `allShots`（每条都带有效 `_index`）后通过。

修完 `node web/_test.js` → **全部功能测试通过（exit=0）**；
`python -B scripts/check_all.py` → **15 组全部通过**（含我上一轮加的 `8b/9` 复核页建议行为检查）。

| 阶段 | 计分命中 | 比分 |

### 我改的测试（`web/_test.js`）

1. 显式设 `win.STORE.backendOk = false; win.STORE.demoMode = true;` —— 让这个**离线单测**
   走本地重算路径。**注意：不要用 `await` 来"修"它**：有后端时本地状态是靠
   `APP_LOAD_JOB` 重新拉产物更新的，node 单测没有后端；而 `await` 会把断言推进微任务，
   这个文件末尾又是同步算 `process.exitCode` 的，结果会变成"打印里有 ✗ 但 exit=0"。
2. 场景 B 的取行改成从 `allShots` 优先（原来从复核队列取，`_index` 可能是 -1 → 被守卫静默挡掉）。

### 建议你们处理的 3 件事（按严重度）

1. **`review.js` 里 `row._index < 0` 时静默 return**（约 143 行）。这不是理论问题：
   页面自己产出的复核行就可能 `_index = -1`（后端 `_shot_event` 不输出 index 字段，
   只能靠 `(t, player_id, value)` 匹配 timeline，一旦某个字段被改过/不一致就匹配不上），
   这时用户点"判为命中/未中/确认此建议"**毫无反应也没有提示**。
   建议：① 匹配不上时退回用 `(t, player_id)` 再匹配一次；② 仍失败就弹一句
   "这条记录无法定位到比赛事件，请刷新后重试"。
2. **timeline 的 `made` 对"结果未知"是 `false`**（`rules.py:360` 的 `made=bool(made)`），
   只能靠 `result="unknown"` / `outcome_unknown` 标签区分。任何直接读 `made` 的下游
   （导出、图表、别处的批量逻辑）都会把"未知"当成"未中" —— 正是你们自己在批量里防的坑。
   建议 `_shot_event` 直接输出 `made: null`（它已经有 `result` 字段），并检查下游消费者。
3. **`POST .../correct` 传 `value=9` 返回 200**（`api.py:763` 只接受 1/2/3，
   越界值被静默忽略但接口报成功）。建议返回 400。

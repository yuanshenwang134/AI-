## 二、穿筐窗口开关：真机 A/B（他们缺的那一步）

由于 `make_window_from_crossing` **没有暴露给 API**（`api.py` / `sources.py` 里都没有），
真机对照只能在进程内注入该配置完成（不改产品代码、不改默认值）：
直接构造 `VideoSource` 跑真视频，off / on 两臂其余参数完全相同。
脚本：`_tmp\ab_crossing_window_real.py`，产物 `out\ab_crossing_real_20260929_1749.json`。

| 素材 | off（现状） | on（开关打开） | 变化 |
|---|---|---|---|
| `game01_seg45` | 5 条（1 进 + 4 未知，含 1 条建议） | 5 条，逐字段相同 | 无 ✓ |
| `fixedcam` | 7 条（3 进 4 未知） | 7 条，逐字段相同 | 无 ✓ |
| `dairy` | 3 条（3 进） | 3 条，逐字段相同 | 无 ✓ |
| **`day_outdoor`** | #2 = `t=13.61 uncertain`，cross=12.646 | **#2 = `t=12.81 make`**，cross=12.646 | **真进球被确认** ✓ |
| `night_outdoor` | 1 条（1 进） | 1 条，逐字段相同 | 无 ✓ |
| `nathan` | 6 条（1 未中 + 5 进） | 6 条，逐字段相同 | 无 ✓ |

**解读**：
1. 这与我上一轮的诊断完全吻合 —— day#2 的**实测穿越全程都在**（横向偏差 3.6px，从筐里穿过），
   只是被"进入时刻锚点 + 0.9s 窗口"挡掉；用穿越本身做锚后即在 **12.81s 确认为命中**。
2. **day 第 3 球（25.83）即使打开开关仍是未知**（那一条压根没有实测穿越）→ 开关只修
   "测到穿越但窗口过期"这一类，与他们的说明一致。
3. **两类机制没有互相污染**：game01 那记（无实测穿越）仍是"未知 + 建议"，没有被开关变成命中；
   day 也没有因此多出建议。
4. 旧项目当年因为这个开关出现过"夜间多出一次假进球"而降级 —— 本轮 night 打开后**没有变化**，
   但那是他们的素材/场景，不能据此说风险消失。
5. off 臂把六段既有基线**逐一复现**了（含 game01 的建议），说明这个 A/B 脚手架本身可信。

**结论口径**：真机证据支持"启用该开关能找回 day 一记真进球且不动其它五段"，
但（a）只覆盖六段，（b）该开关目前**没有 API 入口**，
建议按 `legacy_center_lock` 的做法把它暴露成显式实验参数，再由复核方用产品接口复检一次；
**默认值是否改动由产品决策，我不改。**

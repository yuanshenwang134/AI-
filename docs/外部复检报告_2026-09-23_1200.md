## 1. 残留问题（新发现，按优先级）

### R1 自动建立的基线发生了位移，却没有声明 → 事件表少一条，而 `final` 仍是正确的

**现象**：自动定位（不给 `box`、不给 `start`）时 `final = 38:38`（**与真值一致**），
但事件表里**主队少了一次得分**（事件 7 条、主队增量 +5），用户从产物上看不出来。

**证据**（同一次请求，两种基线；`_tmp/recheck_baseline_compare.json`）：

| | 不给 `start` | 给 `start=31:31` | 人工逐帧真值 |
|---|---|---|---|
| 基线 | **home 33 / away 31**（`baseline_from='video'`） | 31 / 31（`provided`） | 31 / 31 |
| 事件数 | 7 | **8** | 8 |
| 主队增量 | **+5** | **+7** | +7 |
| 客队增量 | +7 | +7 | +7 |
| `final` | 38:38 | 38:38 | 38:38 |
| OCR 命中 | 379 / 480 | 379 / 480 | — |

给 `start` 时的事件明细**完全正确**：`home +2(t=8.01) +2(134.13) +2(157.16) +1(179.68) = +7`、
`away +2(91.59) +1(106.61) +2(138.64) +2(207.71) = +7`。

不给 `start` 时，产物**自身是自洽的**（`33 + 5 = 38` ✓），但**与画面真值不自洽**：
真实开局是 31:31，而基线被定成了 33。

**根因定位**：`scripts/read_marked_scoreboard.py` 的 `build_events()`：
```python
if current[team] is None:
    current[team] = baseline[team] = value      # 每队"第一次可读"即定基线
```
本素材**开头约 8 秒一条读数都没有**（`readings` 首条是 `t=8.01`，此时画面已是 home 33 / away 31；
我独立做的全画面网格扫描也显示 t=1 s 那帧 OCR 只读出 `FHS AHS 31 3 rd Qtr`，FHS 的数字读不到），
于是主队那次 `31→33` 的得分被直接并进基线，事件表少一条。

**这不是"算错"，是"没声明"**：产物对外表现完美（终场 38:38），但用户无法得知"主队基线取自 t=8.01 s、
之前的得分没进事件表"。对复盘类产品来说，这是**静默漏计**，比报错更危险。

**建议修法**：
1. 产物补字段：`baseline_at = {home: 8.01, away: 8.01}`、`baseline_note`；
   只要 `baseline_at > 0`（即首帧没读到），报告与界面上就必须显示
   "基线取自 t=X s 的画面读数，此前的变化未计入事件；如需精确请填起始比分或手动补录"；
2. `start` 未填时，把"起始比分"输入框提示改成**对照画面开头填写**（现在默认用首次读数，静默且不可见）；
3. 可选（补数据）：对开头读不出的帧做一次**降权兜底解析**（位置抽取，`parse_mode='position_fallback'`、
   `confidence=0.5`），命中就用来把基线定在更早的时刻；
4. 产物自检加一条：`baseline_at == 0` 或"必须带基线提示"，二者至少成立一个。

**验收**：不填 `start` 跑 game_04 时，产物必须带 `baseline_at`（本素材为 t≈8 s）与提示文案；
若填 `start=31:31`，事件数必须为 8、主客增量必须各为 7（当前已满足）。

### R2 自动定位框偏大 → OCR 命中 79%（精度问题，**不是**事件丢失的原因）

**现象**：自动定位给出 `box = [384, 64, 1152, 172]`（x 384~1536、y 64~236），
真实比分条在 `x 600~1360, y 100~180`；命中 379/480 = 79%。

**证据**（同一份新代码、同一接口，只换框）：
| 框 | 命中 | 事件数 | 主客增量 | final |
|---|---|---|---|---|
| 自动 `[384,64,1152,172]` | 379/480 | 7 | +5 / +7 | 38:38 |
| 手工收紧 `[600,100,1360,180]` | **425/480** | 7 | +5 / +7 | 38:38 |

**修正上一版报告的说法**：我原先写"收紧框能拿到 10 条事件、主客 +7"，那是**旧代码**的结果——
旧的位置解析会为漏读的数字"补"一个值（正是上一份报告 P0-3 修掉的行为），所以它看起来事件齐全。
新代码收紧框后**事件数不变**（7 条）：**事件少一条的原因是 R1（基线位移），不是框**。
框只影响命中率（379 → 425）。

**建议修法**（仍然是精度改进，优先级低于 R1）：
1. 第一遍 OCR 完成"这里确实是比分"的验证后，用**命中文字的包围盒**自动收紧区域再跑第二遍；
2. 把 `ocr_hit / n_crops` 作为验收指标暴露（建议 ≥0.9），低于阈值时提示"建议手动框选"；
3. 命中率低时报告要如实写"读数覆盖率 79%"，不要只给终场比分。

**验收**：自动定位在 game_04 上 `ocr_hit/n_crops ≥ 0.9`（当前 0.79）。

### R3 报告文案与实际计分口径不符（会误导读者）

**现象**：任务 `8ce2e30437ed`（`score_policy=scoreboard`、无标定）的判定文字是：
```
{"state":"scoreboard","note":"比分由广播比分牌给出（读到 1 帧）；另有 8 次视觉命中已计入总分"}
```
但该任务 `meta.visual = null`、`meta.attempts = null` —— **根本没有视觉层**；
那 8 条是**比分牌事件**（`meta.scoreboard.events` 8 条），不是"视觉命中"。
另外 `meta.scoreboard.frames_read = 1 / frames_hit = 1` 也不反映实际读到的 379/480，
容易让人以为"只读到 1 帧却算出 38:38"，反而降低可信度。

**建议修法**：按 `score_policy` 分别生成文案：
- `scoreboard`：写"带入分 A:B（来源：画面读数/人工输入）+ 比分牌事件 N 条 = 终场 C:D"，
  并给出读数覆盖率；
- 混合口径（比分牌 + 视觉）才提"视觉命中 N 次计入/未计入总分"，并写清哪些计入；
- `meta.scoreboard.frames_read/frames_hit` 应填**OCR 采样帧数与命中帧数**（本例 480 / 379），
  而不是"1"。

**验收**：`score_policy=scoreboard` 的任务，判定文字里不得出现"视觉命中"；读数覆盖率与终场比分能相互解释。

## 2. 复检方自己踩的坑（记录一下，避免下轮误报）

1. **环境变量不带全会产生"假失败"**：`check_video_fit.py` 缺 `YOLO_CONFIG_DIR` 会报
   `[WinError 5] 拒绝访问 ...\AppData\Roaming\Ultralytics`；`probe_footage.py` 缺 `AIHOOP_MODELS`
   会得到 `0/0` 采样与"未完成检测器体检"。两者都不是代码缺陷。**建议**：在脚本里对缺失的关键环境变量**显式报错**，
   而不是退化成一个看起来像"素材不行"的结论。
2. **合成短序列不适合验证事件流**：我用 3 条文本（31→37→38）测 `build_events` 时得到 0 事件，
   那是**正确行为**（+6 超过 `max_delta=3`，真实运行里有中间读数填平）。验收这类逻辑要用**稠密序列**
   或直接跑真实端到端（本轮的 #1/#2 就是真实端到端）。
3. 他的 `tests/test_external_report.py` 会**自己起一个 8019 端口的服务**，与常驻后端并存时可能互相干扰
   （本轮出现过一次探活超时）。建议在文档里写明这一点。
